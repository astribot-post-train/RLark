# Station gateway bootstrap (experimental)

> **Naming (2026-11-12)**: the object in this directory is called a **Site Node** in the UI and in the external API: one machine's long-lived identity and network membership in the site. "Station" is reserved for a station of a Fleet Run, as the paper defines it. The CRD group `station.rlark.io`, the `Station*` kinds and the binary names are kept as code names; the migration and the enrollment design are in [Station v2](../../docs/design/station-v2.zh-CN.md).

This standalone component bootstraps one WireGuard site interface using a Kubernetes DaemonSet. It is not the Station controller, does not integrate with RLark UI, and is not an independent-peer solution. Use only after validating the topology and CIDRs; it has not been tested on production nodes. No systemd or Ansible is involved.

Build the WireGuard image in this directory and deploy it with the network template in `extensions/station/deploy/station-agent.yaml`. Nodes select that template with `station.rlark.io/network=enabled`; desired configuration comes from `station-wireguard-config`, and private keys live under `/var/lib/station/wg/private.key` on each node. Install through a Kubernetes API reachable independently of this tunnel. Verify the host has WireGuard kernel support. Set and verify forwarding, firewall and return routes separately when forwarding traffic; the component does not change host-wide forwarding or firewall rules.

On first start each gateway generates a private key at `/var/lib/station/wg/private.key`, mode 0600; its public key appears in the Pod log. Transfer and independently verify the public keys before configuring the peers; never copy the private key. Restrict host and Kubernetes administrative access, ConfigMap writes and access to the key directory. Each node must have its own hostPath and key. Bootstrap both sides with empty peers first, then update each ConfigMap with the other side's verified key and route. ConfigMaps have no private key.

For operation-owned entries, a config may include top-level `nodeUID` and `publicKey`, and a peer may include `nodeUID`. These fields are non-secret ownership metadata; the gateway validates them but does not use them for authentication. Node removal may delete only an entry whose UID matches the exact Kubernetes Node instance or whose key/address matches a current Node-UID-bound Station observation. Legacy entries without verifiable ownership are left untouched and block automated removal.

For an outbound endpoint that requires a particular source address, `uplinkRoutes` accepts explicit IPv4 host routes, for example `{"destination":"10.11.14.128/32","gateway":"192.168.0.11","source":"192.168.31.250","interface":"enp2s0"}`. The source must already belong to that interface. The gateway adds a route only if no exact route exists; it reuses an exact matching route with its reserved protocol and metric and reports conflicts. It never removes uplink routes, including when configuration is changed or the Pod stops: arrange manual cleanup over an independent management path. A partial failure may leave previously added routes in place. Do not use this setting until return paths and endpoint source selection have been verified.

The program retries reconciliation every 10 seconds, detects ConfigMap changes, and refuses to adopt an interface without the `rlark-station-gateway/v1` link alias. It owns that interface's WireGuard peers and routes using private protocol 242 and metric 49321. These values are not global proof of ownership; it never deletes routes. Before removing a route from the ConfigMap, remove that exact route manually over the independent management path; otherwise reconciliation stops before changing peer configuration. Reserve these values on participating nodes and check for conflicts. It never installs a default route. Route conflicts cause an error rather than replacing existing routes. If the interface already has a different IPv4 address, reconciliation rejects the change before updating peers or uplink routes; it never removes the address. Use a new interface and an independently verified path for address migration. The four current network nodes run the private-registry WireGuard image with this check; other installations require a rebuilt image and the two-container Station Pod template. Do not run a second network manager against the same interface. An invalid config is logged and retried; the last successfully applied kernel configuration remains, but a failure after partial application can leave a partial update. There is no automatic rollback or connectivity verification. For recovery, retain an independent SSH/Kubernetes management path and use the previous ConfigMap; restoring connectivity is not guaranteed while the node, K8s API, image or ConfigMap is unavailable. It does not remove the interface on exit or uninstall. If the process crashes after creating a link but before marking its alias, it refuses to adopt the unmarked link; an administrator must inspect and remove it using the independent management path before retrying.

Check Pod logs, `wg show`, explicit routes, bidirectional handshake, traffic and MTU before relying on the connection. Test Pod and node restarts, an invalid config, a conflicting route, return paths and management recovery in a non-production environment. Restrict allowed networks to the required prefixes. Do not put secrets in this ConfigMap or logs. Network access alone is not authorization.

The source provides `/station-gateway --status` for read-only diagnostics without the `wg` CLI. It reads the interface name from the configured JSON and queries the kernel; JSON output contains interface and peer public keys, peer handshake time (UTC or `null` if never observed), and receive/transmit byte counters. It omits private and preshared keys, endpoints and allowed networks. It requires permission to query WireGuard in the gateway's network namespace and fails if the device or configuration cannot be read. A recent handshake does not prove end-to-end application health. This command requires a newly built image; the current private-registry WireGuard image includes and has been tested with it.

Tests run independently of the root Go workspace: `GOWORK=off go test ./...` and `GOWORK=off go vet ./...`. Run the real kernel test only in a disposable network namespace: `unshare -Urn env GOWORK=off STATION_NETNS_TEST=1 go test -v -run TestKernelReconciliation ./...`. Root workspace test targets do not automatically test this standalone module.

On 2026-11-11 the kernel reconciliation and status tests passed in a disposable Docker network namespace with only `CAP_NET_ADMIN` added and networking disabled. They covered idempotent reconciliation, rejection of address changes and conflicting routes, preservation of foreign routes/interfaces, retry after restoring the original config, status output from a real kernel WireGuard device, and a missing-device error. The image build was also completed with `--network=none` after adding `status.go` to the build context. The host disallowed `unshare --net`, so the tests ran inside Docker; this remains an isolated kernel test, not a production-node restart or recovery test.

The example includes an exec readiness probe (`/station-gateway --check`). The process writes a container-local readiness record after a successful reconciliation; the probe requires that record to be no more than 30 seconds old and match the current config bytes. Failed reconciliation clears it, and a changed config becomes unready until reconciled. Readiness publication requires a writable container `/tmp`. This only reports recent local reconciliation: it does not verify peer handshakes, routing end-to-end or service availability, and a failure to clear the file can leave it valid until its freshness deadline. It is not an automatic rollback or a liveness probe. Existing deployments must use a newly built image and add the probe explicitly; older cached images do not support `--check`.

## Station Pod deployment (example)

`extensions/station/deploy/station-agent.yaml` provides two mutually exclusive DaemonSets. Nodes without `station.rlark.io/network=enabled` run the identity container only; labeled nodes run identity and WireGuard containers in one host-network Pod. Each container uses its own private-registry image. The WireGuard container alone receives `NET_ADMIN`. Changing the label replaces the Pod and can interrupt service; it does not remove an interface or route.

The source supports an optional `STATION_GATEWAY_OBSERVATION_FILE` in a shared `emptyDir`. After successful reconciliation it writes the program's own sha256 and document level (`documentLevel` in `main.go`: the newest configuration document it understands), the owned interface's public key, kernel addresses, the collection time and, for every peer, its public key, last handshake time and received and sent byte counts: a hub's counts are the only account of a leaf that has dropped off. It contains no private or preshared key, endpoint or allowed address. The identity container reads it with `--wireguard-observation-file`; missing, invalid or more than 30-second-old snapshots clear the WireGuard observation without stopping identity heartbeats. The volume contains no private key. The reported Station timestamp is the server receipt time, not the snapshot collection time. This data path requires rebuilt images and an updated DaemonSet; it does not itself provide a user-facing address API or UI.

The Station identity source also contains an internal network summary reader. It rechecks the current member Node UID and active Station binding, requires matching cluster, Node, Station and binding-version observation ownership, and marks a receipt older than 90 seconds stale. Older observations without a binding version are rejected until a fresh report is stored. The internal `POST /v1/internal/node-network` is disabled by default; `station-api --gateway-credential-file=PATH` enables it with a dedicated bearer credential of 32 to 4096 non-whitespace characters, read from the file for each request. Configure Gateway with `--station-api-address`, `--station-api-ca-file` and `--station-gateway-credential-file`; its credential file must contain the same value. Protect the files as Secrets and use a distinct, randomly generated credential over verified TLS. Provisioning and live deployment are not included in this example. Without this integration the UI displays unavailable network data.

On 2026-11-11 this integration was deployed on the local `cailiang` node and tested through the existing 5173 proxy with an authenticated user request. The Gateway container was replaced manually; the stopped `rlark-gateway-before-wg-observation` container is retained for rollback. The local Station DaemonSet's revision 5 contains its previous configuration. Cloud and robot network DaemonSets were subsequently upgraded and all four nodes returned verified WG addresses through the 5173 proxy. The cloud node 1, cloud node 2 and robot runtimes each completed a pull with `imagePullPolicy: Always` and no pull Secret through the WG-only Distribution endpoint at `http://10.254.240.1:5443`. This endpoint binds only the local WG address, has no registry authentication or TLS, and permits any connected WG peer to pull or push. The company-LAN registry at `10.11.14.128:5443` retains its original TLS and authentication. The WG endpoint still depends on the local host and tunnel: loss of the robot image cache or a fresh robot before WG bootstrap needs an independent image source, and whole-host restart recovery is not yet tested. Recreating Gateway from an older Compose definition can remove the new configuration; reconcile the deployment definition before relying on automated recreation.

Before use, create `station-wireguard-config` with a `<node-name>.json` key for every network node, replace the image references, and set the hostPath to the directory holding that node's existing `private.key`. The example uses a common hostPath across network nodes; clusters with different existing key directories require an explicitly verified migration or per-node deployment. Do not run the old gateway and replacement against the same interface. `STATION_GATEWAY_CONFIG` selects the config file for both the main process and readiness check. Readiness only indicates recent local reconciliation, not end-to-end connectivity. The current site manifests use the WG-only registry; its bootstrap dependency and recovery limits are described above.

The network template uses `/var/lib/station/wg/private.key` on each node and the Station identity container listens for probes on `:18082`, avoiding the default `:8081` when a host-network controller uses that port. The ordinary identity-only template retains `:8081`. The agent's `--probe-address` flag can select another TCP address; listener conflicts stop the agent at startup. A node must have the correct existing key before a migration; do not silently replace its identity.

On 2026-11-11, the local `cailiang` node was migrated to the two-container network Pod. Its existing key was copied into the uniform directory and checked for equality and mode 0600. Pod recreation returned to Ready, and three peer handshakes and tunnel pings were observed. The earlier remote pull failures were resolved by the WG-only registry described above. Whole-node restart and remote cold recovery are not verified.

## Configuration sources after enrollment (2026-11-12)

With `STATION_GATEWAY_COMPUTED_CONFIG` set, the gateway takes the first document that exists and parses: the one station-agent fetched from Station API → `last-applied.json`, this node's copy of the last one it reconciled (beside the private key, so a restart without Station API brings the same tunnel back) → the static `--config` file (bootstrap and rollback; may be absent). Without the variable only the static file is read, as before.

- `STATION_GATEWAY_IDENTITY_FILE`: the public key is written there at start for station-agent to enroll; it no longer has to be copied from the log.
- Peers are updated one by one: only peers that differ are sent to the kernel and dropped peers are removed explicitly; unchanged peers keep their sessions and learned endpoints.
- `STATION_GATEWAY_PRUNE_ROUTES=true` (off by default): routes the configuration drops are removed by the gateway, limited to routes on the interface it created and marked, with protocol 242 and metric 49321. When off the previous behaviour holds: such a route stops reconciliation until removed by hand. Uplink routes, which are on another interface, are never removed.

The document format is produced by `extensions/station/network`; both sides share `testdata/computed-s1u-01-x86.json` as a contract test.
