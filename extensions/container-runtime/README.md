# RLark container-runtime extension

This is an independently buildable Go module for moving Docker and Raw runtime implementation out of the native RLark module. Its API uses the `containers.rlark.io/v1alpha1` group and companion resources pinned to native object UIDs. It reuses RLark's exported execution contracts; native RLark remains a versioned dependency and contains only generic ownership dispatch.

Current contents are an extraction copy of preview Docker/Raw runtime, allocation and supervisor packages, typed companion API/CRDs, UID/tenant binding checks, validation controller, allocation fence, a dedicated mTLS observation endpoint and a Linux foreground Raw Agent. The endpoint trusts only a verified client certificate signed by its configured Agent CA and writes status for the exact current ContainerNode UID, credential, native references, tenant, private address, target release and operator GPU allowlist. The Agent observes the current cgroup-v2 CPU/memory boundary, visible GPU UUIDs and private supervisor occupancy, then retries authenticated heartbeats with bounded backoff. It fails closed when the supervisor or GPU observation is unavailable and never treats visible GPUs as entitlement. The companion allocation package implements an API-backed exclusive per-native-Node lock, exact-UID recovery, legacy reservation fencing and cleanup-confirmed release. These are primitives: enrollment/certificate issuance, the Job scheduler, workload dispatch, cleanup reporter, release hosting/rollout and UI are not wired together. This module is not a working scheduler. Native Jobs that declare `rlark.io/controller-owner: containers.rlark.io` fail closed if the extension owner is not installed. Production onboarding, allocation dispatch, cleanup reporting, release hosting/rollout, UI and safe live-data migration remain incomplete. Do not deploy this module as a production scheduler.

Run `make test`, `make vet`, `make build`, or `make generate-crds` here. `make build` writes `bin/container-runtime-controller`, `bin/container-runtime-api`, `bin/container-runtime-agent`, and `bin/raw-supervisor`; it does not package or install them on container hosts. The API command requires a TLS server certificate, a dedicated Agent client CA, and a kubeconfig/service account with the narrow permissions in `config/rbac/`. The endpoint listens on `POST /v1/heartbeat`. Start the Linux Agent with an HTTPS origin, node certificate/key, server CA, version, private address and private Raw supervisor socket. It observes before every heartbeat, retries transient failures, and requires the supervisor status to prove occupancy; there is no `--allow-no-gpu` or idle fallback. Agent certificate issuance, enrollment, deployment wiring and release rollout remain operator-managed and are not integrated with RLark's native Server. `GOWORK=off` is used to prove the module resolves from its own `go.mod` and `go.sum`.

The detailed target, rollout, cloud test constraints and acceptance gates are maintained in the paired RLark developer plan at `../../apps/rlark/docs/developer-guide/raw-container-runtime-plan.md` and its Chinese counterpart.
