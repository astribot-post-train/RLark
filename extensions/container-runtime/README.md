# RLark container-runtime extension

This is an independently buildable Go module for moving Docker and Raw runtime implementation out of the native RLark module. Its API uses the `containers.rlark.io/v1alpha1` group and companion resources pinned to native object UIDs. It reuses RLark's exported execution contracts; native RLark remains a versioned dependency and contains only generic ownership dispatch and a narrow Host dependency interface.

Current contents are an extraction copy of preview Docker/Raw runtime, allocation and supervisor packages, typed companion API/CRDs, UID/tenant binding checks, validation controller, a durable single-target reservation planner, a Raw Job controller, cleanup receipts, a dedicated mTLS observation endpoint and a Linux foreground Raw Agent. The endpoint trusts only a verified client certificate signed by its configured Agent CA and writes status for the exact current ContainerNode UID, credential, native references, tenant, private address, target release and operator GPU allowlist. The Agent observes the current cgroup-v2 CPU/memory boundary, visible GPU UUIDs and private supervisor occupancy, then retries authenticated heartbeats with bounded backoff. It fails closed when the supervisor or GPU observation is unavailable and never treats visible GPUs as entitlement. The companion allocation package implements an API-backed exclusive per-native-Node lock, exact-UID recovery, legacy reservation fencing and cleanup-confirmed release. With both `--enable-job-reservations=true` and `--enable-task-execution=true`, the preview path can execute one strictly validated Raw process Task through the node-scoped mTLS Task channel and existing Host/Coordinator/supervisor; the execution API only revalidates an existing allocation and cannot create one. Automatic enrollment/renewal, release rollout, authorized logs/stats, UI, Ray/RLinf groups and multi-replica scheduling remain incomplete. This module is not a production scheduler. Native Jobs that declare `rlark.io/controller-owner: containers.rlark.io` fail closed if the extension owner is not installed.

Run `make test`, `make vet`, `make build`, or `make generate-crds` here. `make build` writes `bin/container-runtime-controller`, `bin/container-runtime-api`, `bin/container-runtime-agent`, `bin/container-runtime-admin`, and `bin/raw-supervisor`; it does not package or install them on container hosts. The API command requires a TLS server certificate, a dedicated Agent client CA, and a kubeconfig/service account with the narrow permissions in `config/rbac/`. The endpoint listens on `POST /v1/heartbeat`. Start the Linux Agent with an HTTPS origin, node certificate/key, server CA, version, private address and private Raw supervisor socket. It observes before every heartbeat, retries transient failures, and requires the supervisor status to prove occupancy; there is no `--allow-no-gpu` or idle fallback. Agent certificate issuance, enrollment, deployment wiring and release rollout remain operator-managed and are not integrated with RLark's native Server. `GOWORK=off` is used to prove the module resolves from its own `go.mod` and `go.sum`.

The standalone controller defaults to validation-only. It uses Lease leader election in `rlark-system`; configure `--leader-election-namespace` and the controller RBAC manifest when using another namespace. `--enable-job-reservations=true` opts into the isolated preview controller with an uncached API client. The API and Agent each require their own `--enable-task-execution=true` flag for scoped execution; apply `config/rbac/container-runtime-api-execution.yaml` only for this preview. The controller materializes one Raw process Task, checks selectors/identity/tenant, aggregates current Running/Succeeded/Failed observations, and releases an allocation only after durable supervisor cleanup, an exact cleanup proof and observed deletion. Completed Task identity is retained so a restart cannot rerun it; suspension, deletion, template changes and explicit restart retire it through the existing cleanup workflow. The optional native `ControllerExtension()` remains validation-only. Stopping the controller leaves reservations intact. Task transport is deliberately limited to the exact certificate-bound allocation and Task; arbitrary Kubernetes reads, watches, discovery, secrets, proxying and allocation creation are denied. Automatic enrollment, release rollout, logs/stats, UI, Ray/RLinf groups and multi-replica scheduling remain incomplete.

The detailed target, rollout, cloud test constraints and acceptance gates are maintained in the paired RLark developer plan at `../../apps/rlark/docs/developer-guide/raw-container-runtime-plan.md` and its Chinese counterpart.

The independent `container-runtime-admin` command provides explicit administrator creation of a separate Cluster, registration of one authorized Raw node, and offline node certificate/package export. Every create uses a caller-retained operation UUID; foreign objects, replacement UIDs, conflicting tenants or credentials are never adopted. Packages contain only node credentials, public server CA, checked Linux artifacts and separate Agent/supervisor launchers. No management kubeconfig or issuer key is exported. Automatic enrollment, renewal, Docker packaging and rolling upgrades remain incomplete. See the paired plan documents for strict JSON requests, prerequisites, command examples and limits.

Copy the templates in `config/examples/`, replace their `REPLACE_...` values from authoritative reads, and run `cluster-create`, `node-register`, then `node-package` with the administrator kubeconfig. Keep each operation UUID unchanged when retrying a lost response. Transfer the resulting package privately, verify `SHA256SUMS`, start `start-supervisor`, and then start `start-agent`; the command does not mark a node Ready or dispatch a Job.

Authenticated release publication is opt-in: start both the independent API and controller with `--artifact-directory=/private/agent-artifacts`, mounting the same operator-managed tree read-only. Existing RBAC permits release reads and controller status patches; Agents receive no Kubernetes RBAC. Copy `config/examples/agent-release.yaml`, replace all placeholders and its architecture if necessary, publish the corresponding Linux Agent binary at `releases/agent-v1`, and set the matching lowercase SHA-256. Create the immutable AgentRelease in the ContainerCluster namespace with the same tenant label. Wait for current-generation `Available=True` before an administrator changes that ContainerCluster's `spec.targetAgentRelease` to `agent-v1`. Use a new record/path for a new version; do not replace published bytes. Missing or corrupt files revoke availability on periodic inspection.

With the store configured, `POST /v1/release` accepts only the authenticated node's current target. The strict body is `{"action":"manifest","os":"linux","architecture":"amd64"}`; `action: download` additionally requires the manifest's `releaseUID` and `sha256`. No target returns 204. The client methods `TargetRelease` and `DownloadRelease` validate the manifest and exact bounded Linux executable bytes and refuse redirects. The route is absent without a store. This is authenticated artifact delivery only: the foreground Agent does not yet poll these methods or install, switch, roll back or renew itself. Targeting a newer version can fence scheduling until the operator installs it and fresh heartbeats confirm readiness; it does not stop or free an existing execution. Keep the supervisor running during Agent-only changes. The paired developer documents describe publication, rejection/recovery behavior and the remaining rolling-upgrade gate.
