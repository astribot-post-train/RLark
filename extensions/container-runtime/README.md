# RLark container-runtime extension

This is an independently buildable Go module for moving Docker and Raw runtime implementation out of the native RLark module. Its API uses the `containers.rlark.io/v1alpha1` group and companion resources pinned to native object UIDs. It reuses RLark's exported execution contracts; native RLark remains a versioned dependency and contains only generic ownership dispatch and a narrow Host dependency interface.

Current contents are an extraction copy of preview Docker/Raw runtime, allocation and supervisor packages, typed companion API/CRDs, UID/tenant binding checks, validation controller, a durable single-target reservation planner, a Raw Job controller, cleanup receipts, a dedicated mTLS observation endpoint and a Linux foreground Raw Agent. The endpoint trusts only a verified client certificate signed by its configured Agent CA and writes status for the exact current ContainerNode UID, credential, native references, tenant, private address, target release and operator GPU allowlist. The Agent observes the current cgroup-v2 CPU/memory boundary, visible GPU UUIDs and private supervisor occupancy, then retries authenticated heartbeats with bounded backoff. It fails closed when the supervisor or GPU observation is unavailable and never treats visible GPUs as entitlement. The companion allocation package implements an API-backed exclusive per-native-Node lock, exact-UID recovery, legacy reservation fencing and cleanup-confirmed release. With both `--enable-job-reservations=true` and `--enable-task-execution=true`, the preview path can execute one strictly validated Raw process Task through the node-scoped mTLS Task channel and existing Host/Coordinator/supervisor; the execution API only revalidates an existing allocation and cannot create one. Automatic enrollment/renewal, authorized logs/stats, UI, Ray/RLinf groups and multi-replica scheduling remain incomplete. Target-driven idle Agent rollout is an opt-in preview and does not make cloud acceptance production-ready. This module is not a production scheduler. Native Jobs that declare `rlark.io/controller-owner: containers.rlark.io` fail closed if the extension owner is not installed.

Run `make test`, `make vet`, `make build`, or `make generate-crds` here. `make build` writes `bin/container-runtime-controller`, `bin/container-runtime-api`, `bin/container-runtime-agent`, `bin/container-runtime-admin`, and `bin/raw-supervisor`; it does not package or install them on container hosts. The API command requires a TLS server certificate, a dedicated Agent client CA, and a kubeconfig/service account with the narrow permissions in `config/rbac/`. The endpoint listens on `POST /v1/heartbeat`. Start the Linux Agent with an HTTPS origin, node certificate/key, server CA, version, private address and private Raw supervisor socket. It observes before every heartbeat, retries transient failures, and requires the supervisor status to prove occupancy; there is no `--allow-no-gpu` or idle fallback. Agent certificate issuance, enrollment and deployment wiring remain operator-managed and are not integrated with RLark's native Server. `GOWORK=off` is used to prove the module resolves from its own `go.mod` and `go.sum`.

The standalone controller defaults to validation-only. It uses Lease leader election in `rlark-system`; configure `--leader-election-namespace` and the controller RBAC manifest when using another namespace. `--enable-job-reservations=true` opts into the isolated preview controller with an uncached API client. The API and Agent each require their own `--enable-task-execution=true` flag for scoped execution; apply `config/rbac/container-runtime-api-execution.yaml` only for this preview. The controller materializes one Raw process Task, checks selectors/identity/tenant, aggregates current Running/Succeeded/Failed observations, and releases an allocation only after durable supervisor cleanup, an exact cleanup proof and observed deletion. Completed Task identity is retained so a restart cannot rerun it; suspension, deletion, template changes and explicit restart retire it through the existing cleanup workflow. The optional native `ControllerExtension()` remains validation-only. Stopping the controller leaves reservations intact. Task transport is deliberately limited to the exact certificate-bound allocation and Task; arbitrary Kubernetes reads, watches, discovery, secrets, proxying and allocation creation are denied. Automatic enrollment, logs/stats, UI, Ray/RLinf groups and multi-replica scheduling remain incomplete; idle Agent rollout is an opt-in preview described below.

The detailed target, rollout, cloud test constraints and acceptance gates are maintained in the paired RLark developer plan at `../../apps/rlark/docs/developer-guide/raw-container-runtime-plan.md` and its Chinese counterpart.

The independent `container-runtime-admin` command provides explicit administrator creation of a separate Cluster, registration of one authorized Raw node, and offline node certificate/package export. Every create uses a caller-retained operation UUID; foreign objects, replacement UIDs, conflicting tenants or credentials are never adopted. Packages contain only node credentials, public server CA, checked Linux artifacts and separate Agent/supervisor launchers. No management kubeconfig or issuer key is exported. Automatic enrollment, renewal and Docker packaging remain incomplete. The opt-in `--enable-agent-rollouts=true` controller can select one fresh idle Raw node at a time after `spec.targetAgentRelease` is set; install the additive rollout RBAC and enable upgrade reservations first. It will not adopt foreign/manual operations, preempt workloads, or reap a completed operation until the updater acknowledges its persisted terminal journal and exact allocation deletion is observed. See the paired plan documents for strict JSON requests, prerequisites, command examples and limits.

Copy the templates in `config/examples/`, replace their `REPLACE_...` values from authoritative reads, and run `cluster-create`, `node-register`, then `node-package` with the administrator kubeconfig. Keep each operation UUID unchanged when retrying a lost response. Transfer the resulting package privately, verify `SHA256SUMS`, start `start-supervisor`, and then start `start-agent`; the command does not mark a node Ready or dispatch a Job.

Authenticated release publication is opt-in: start both the independent API and controller with `--artifact-directory=/private/agent-artifacts`, mounting the same operator-managed tree read-only. Existing RBAC permits release reads and controller status patches; Agents receive no Kubernetes RBAC. Copy `config/examples/agent-release.yaml`, replace all placeholders and its architecture if necessary, publish the corresponding Linux Agent binary at `releases/agent-v1`, and set the matching lowercase SHA-256. Create the immutable AgentRelease in the ContainerCluster namespace with the same tenant label. Wait for current-generation `Available=True` before an administrator changes that ContainerCluster's `spec.targetAgentRelease` to `agent-v1`. Use a new record/path for a new version; do not replace published bytes. Missing or corrupt files revoke availability on periodic inspection.

With the store configured, `POST /v1/release` accepts only the authenticated node's current target. The strict body is `{"action":"manifest","os":"linux","architecture":"amd64"}`; `action: download` additionally requires the manifest's `releaseUID` and `sha256`. No target returns 204. The client methods `TargetRelease` and `DownloadRelease` validate the manifest and exact bounded Linux executable bytes and refuse redirects. The route is absent without a store. Binary installation is opt-in preview functionality described below. An immutable AgentUpgrade operation and typed upgrade allocation now compete on the same node lock as workloads; local idle observation alone cannot authorize a switch. Targeting a newer version can fence scheduling until the operator installs it and fresh heartbeats confirm readiness; it does not stop or free an existing execution. Keep the supervisor running during Agent-only changes. The paired developer documents describe publication, rejection/recovery behavior and the remaining rolling-upgrade gate.

For explicit upgrade reservations, install the updated CRDs/RBAC, start the controller with `--enable-agent-upgrade-reservations=true`, fill `config/examples/provision-upgrade.json`, and run `container-runtime-admin upgrade-create --kubeconfig=/private/admin/kubeconfig --config=...`. Retain the operation UUID on retry. Inspect the resulting AgentUpgrade and its exact allocation with the administrator kubeconfig. Reservation and cancellation are supported: deleting a Pending/Reserved operation waits for proven allocation deletion, while an Applying/uncertain operation remains protected. Task transport cannot execute or release an upgrade allocation. With the additive `config/rbac/container-runtime-api-upgrades.yaml` and API flag `--enable-agent-upgrades=true`, node-scoped `POST /v1/upgrade` supports assignment/get, CAS claim by retained attempt UUID, and authenticated success/rollback receipts. The controller alone releases the exact lock after a fresh idle version proof and observed deletion; it retains completed operations for administrator review. Applying with uncertain results remains protected. The Linux Agent supports opt-in local binary switching and restart recovery; automatic rolling selection is available only through the separate opt-in rollout controller; cloud rollout acceptance remains outstanding. See the paired plan for exact references, retry semantics and HTTP errors.

To export an upgradable node package, set `enableUpgrades: true` (default false). Before starting the Agent, create `<stateDirectory>-agent-upgrades` owned by root with mode 0700, separate from supervisor/workload paths. The generated launcher passes `--enable-agent-upgrades=true`, `--agent-install-path=<installDirectory>/container-runtime-agent` and `--upgrade-state-directory=<stateDirectory>-agent-upgrades`. The serial heartbeat loop polls/claims only a scoped Reserved operation, persists its attempt before sending, verifies the current immutable release and downloads, then fsyncs a staged binary, backup, journal and atomic installation. It preserves argv/environment on exec and leaves the supervisor running. A failed exec restores the source; the next fresh idle heartbeat permits rollback completion. The retained receipt derives the running version from `/proc/self/exe`, so bootstrap `--version` arguments remain valid across service restarts. Keep the journal and private switch checksum files: the opt-in launcher accepts only the export digest or updater-verified source/target digest while checking all other package files. Locks fence concurrent updaters; foreign credentials/paths, corrupt bytes and uncertain state retain the allocation. Automatic timeout rollback after a new binary starts, power-loss rollback under systemd, and cloud upgrade validation are still incomplete. The rollout selector is preview-only and requires explicit enablement; it serializes selection and waits for updater journal acknowledgement before reaping success. This is preview infrastructure, not unattended rollout support.

For target-driven idle rollouts, install the regenerated ContainerCluster/AgentUpgrade CRDs and `config/rbac/container-runtime-controller-rollouts.yaml`, then enable both controller flags `--enable-agent-rollouts=true --enable-agent-upgrade-reservations=true`. Upgrade the mTLS API first; the API and node updater each need their own upgrade flag. Old Agents without the enabled `agent-upgrade-v1` and matching `agent-platform/<os>/<architecture>` capabilities are skipped. Omitted/zero `maxUnavailable` means one simultaneous upgrade; only 0 and 1 are supported. This limits upgrade concurrency, not overall schedulable capacity: the existing target-version fence can exclude old-version nodes. Nodes with busy/stale observations or held allocations wait without preemption.

The selector persists an immutable operation in the exclusive Cluster slot. Success needs authenticated completion, observed allocation deletion, and a separate `acknowledge` proving the updater's terminal journal was saved. The controller saves one bounded `status.lastAgentUpgrade` receipt before deleting its own successful operation, observes deletion, then selects the next member. Completion/acknowledgement/status/delete response loss remains recoverable. Manual/foreign operations, rollback and uncertain application are retained for administrator recovery. Target changes only remove unassigned operations with no allocation witness; exposed assignments require explicit recovery to avoid stranding pre-claim journals. Inspect `AgentRolloutReady` and `status.lastAgentUpgrade`; all current members must freshly report the target version for readiness. Cloud rolling upgrade and external-supervisor acceptance remain outstanding.
