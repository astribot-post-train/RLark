## Connecting a robot x86 to the LAN

`robot-x86-network.py` configures a routed /32 address through the robot's Orin using IPv4 forwarding and proxy ARP. It is not a layer-2 bridge. The management host needs Python 3 and OpenSSH; both devices need Python 3, NetworkManager, sudo and SSH access. The Orin also needs systemd and iptables. The script uses SSH host-key checking and interactive authentication; it never stores passwords. Verify the host fingerprints through a trusted channel on first connection.

Reserve a unique x86 address outside the router's DHCP pool and confirm it is unassigned. A failed ping does not prove availability. For example:

```bash
python3 docs/design/station-deploy/robot-x86-network.py check --orin 192.168.31.5 --external 192.168.31.251
python3 docs/design/station-deploy/robot-x86-network.py apply --orin 192.168.31.5 --external 192.168.31.251 --address-reserved
ping 192.168.31.251
ssh astribot@192.168.31.251
```

Use `--help` for LAN, internal address and username overrides. The script identifies the internal and LAN interfaces separately, preserves existing addresses and the x86 default route, and installs address-scoped forwarding rules. It backs up the original settings under `/var/lib/rlark-robot-x86-network/` on each host; do not edit or remove these files. Repeating `apply` repairs an interrupted operation. If an unrelated configuration or rule conflicts, it stops for manual inspection. To undo, run `restore` with the same address arguments; it refuses to overwrite subsequent profile edits. If one host is unavailable, restore it by rerunning the command after connectivity returns. Verify service reachability and firewall policy after deployment; host firewalls, network isolation or later firewall reloads may block traffic. The scripts configure persistent state, but a reboot must be tested separately.

## Station API Prototype

Historical prototype notes (see the current deployment above): `station-api.yaml`, `management-rbac.yaml` and `member-rbac.yaml` are example Kubernetes manifests in `extensions/station/deploy`. They pass `kubectl create --dry-run=client` but have not been applied. Build the binary or image with `make -C apps/rlark station-api` or the RLark Docker build. The workload mounts `station-management-kubeconfig`, `station-api-tls`, `station-api-database` and `station-api-database-ca` Secrets; their values are intentionally absent from these files. The DSN must use `sslmode=verify-full` and point `sslrootcert` at `/var/run/secrets/station-db/ca.crt`. The TLS certificate must cover the Service DNS name. The service is ClusterIP only, so cross-site agent reachability and the certificate SAN for that path remain unresolved.

The management kubeconfig identity must be the user `station-api` and receive only the grants in `management-rbac.yaml`. Create member kubeconfig Secrets in the management API's `station-member-credentials` namespace. Each Secret must be named `station-member-` plus lowercase unpadded base32 of the first 10 bytes of SHA-256(cluster ID), carry annotation `station.rlark.io/cluster-id` equal to its Cluster object name, and contain `kubeconfig`, `service-account-namespace`, `service-account-name`, `service-account-uid` and `audience`. The member kubeconfig uses the restricted `station-api-reader` permissions in `member-rbac.yaml`; it must use verified HTTPS and inline trust/credentials. The API re-reads the Secret and refreshes its client after content rotation, but no rotation automation exists. The station-agent identity is a separate ServiceAccount and must use a Pod-bound token with audience `station.rlark.io`.

`station-agent.yaml` is a prototype DaemonSet. Replace the ConfigMap endpoint and registered Cluster object name, choose a trusted CA Secret named `station-api-ca`, and set its `ca.crt`; the endpoint must match that CA and be reachable from every member node. The agent reads the projected `station.rlark.io` token for every request, so projected-token rotation is observed without restarting the Pod. It connects directly without environment proxies, rejects redirects, and reports kernel boot time parsed from `/proc/stat` as informational observation data. Invalid or unavailable `btime` prevents that report and triggers retry. It sends no claimed Node name; the API resolves the bound Pod and Node. Hardware identifiers, WireGuard peer and probe telemetry are not collected. The health endpoints listen on Pod port 8081 for Kubernetes probes; readiness tracks a recent successful API report. The local agent is deployed and has reported to the real API.

Provision `station_api.challenges` from `apps/rlark/config/station-api-challenges.sql` with a separate migration owner. The `station-api-database` Secret's `dsn` must use a runtime role with only schema usage and table SELECT/INSERT/UPDATE; do not grant runtime DELETE. Expired challenge pruning needs a separately scheduled janitor identity. The administrator Rebind submission endpoint is implemented in Gateway but is not deployed or wired to the console; live operations require the Station CRD and controller. Until a production `SensitiveAuthorizer`, action adapter and audit path exist, challenge and sensitive routes remain fail closed; the Station API prototype currently accepts only authenticated Observations. These manifests have only passed client-side parsing, not live RBAC, TLS, database, or CRD status-write validation.
