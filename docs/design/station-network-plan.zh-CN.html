Design proposal · extensions/station

Station、跨集群网络与存储

给每台机器一个长期不变的 Station 编号，让重启、重建和换硬件都有明确的处理规则；同时用Station Pod 的独立 WireGuard 容器管理网络，和业务容器完全隔开，像 rlark node-agent 一样单独部署。个人代码和大文件放 NAS，Fleet 共享业务数据使用现有 PostgreSQL 实例的独立数据库和账号。先恢复迁网后的本地集群，再推进跨站接入。Station 拟作为独立扩展，RLark UI 入口改动范围待实现验证；Fleet 数据迁移另需修改 Fleet。

01结论与决策

本稿基于对 RLark 代码的核对，以及与 Codex 的多轮讨论（网络、Station、存储）。

只新增，不改 RLark

Station 新组件拟放在 extensions/station/，使用独立 API group station.rlark.io；UI 入口预计修改 5 个文件，实际集成范围待验证。Fleet 数据层另需改造。

Station 由节点证据决定

阶段 0：以 Cluster + Node UID 建立 Station，UID 变化就等管理员确认，不用同名自动接管。节点 UID 只标识 K8s 对象，不能认证上报者；可信节点认证与防重放方案在配置下发前必须落实，具体机制待验证。

WireGuard 完全由 K8s 管理

Station 使用独立 DaemonSet 模板，和业务容器隔开。公钥和期望配置由 K8s 声明，私钥只留节点本地；网络容器在宿主机网络命名空间应用 WireGuard，不依赖 systemd 或 Ansible。

现在做（阶段 0 + 阶段 1）

  • 节点以 Cluster + Node UID 自动创建 Station；UID 变化交管理员确认，不能同名自动接管
  • 上报用每集群 API key（服务端存哈希），走 TLS / 加密网络传输
  • UI 委托 Gateway /users/me 验证身份，写操作只开放给管理员
  • station-agent DaemonSet 独立管理声明式 WireGuard；私钥留本地，路径只观测、不自动切换
  • 机器人开发须有人现场照看；确认动作入口、VR 接管、急停和断联安全行为
  • 个人代码和大文件放 NAS；操作、事件和采集元数据使用现有 PostgreSQL 实例的独立数据库与账号
  • 保留 Distribution + KS3；所有获凭证节点均可推拉，仅向受信任节点分发凭证

以后再加

  • 更强硬件身份验证；节点认证及防重放须先满足配置下发门槛
  • station-agent 内置路径探测的自动回退（阶段 0 只观测，实测后再开启）
  • 管理员重绑、完整审计历史、更细的租户授权
  • Worker 租约、epoch 和旧指令隔离（依赖统一轨迹层落地）
  • KPFS 跨站共享；Harbor 按只读权限、审计等实际需求再评估
  • 本地站点镜像层缓存（机器人跨站重复拉取成为瓶颈时再加）

待验证

  • 机器人 x86 经 Orin、路由器两层 NAT 拨出的 UDP 可达性和 MTU
  • 金山云、百度云是不是 K8s 节点（决定 station-agent 能不能跑上去）
  • 控制面节点上运行特权 DaemonSet 是否被允许
  • 机器人动作是否有其他进程可绕过统一下发口
  • sgw-ksyun 安全组开放 UDP 51821 的流程
  • 云端经 WireGuard 读 NAS 代码的启动耗时、缓存一致性和 PostgreSQL 恢复
  • Distribution 恢复旧地址相关的入口、证书和节点信任；redirect 的兼容性与跨站下载

使用两个互斥的 DaemonSet：未标记网络角色的节点只运行 Station 身份容器；标签 station.rlark.io/network=enabled 的网关或独立 Peer 节点，在同一 Pod 中额外运行 WireGuard 容器。两种容器使用各自的私有仓库镜像，WireGuard 容器单独获得 NET_ADMIN；网络 Pod 使用 hostNetwork。切换标签会重建 Pod，并非无中断切换。

网络容器读取 ConfigMap 中以节点名命名的配置；私钥保留在各节点原有 hostPath。切换前必须核对各节点实际私钥路径和配置，避免旧网关与新容器同时协调同一接口。网络容器本地就绪不证明端到端连通，身份心跳也不等同于网络健康。角色切换不会自动删除接口或路由。

路由与 AllowedIPs

原设计让独立 Peer 的 /32 和站点网关的 /24 叠在同一个接口上，节点离线后回程会被丢掉。现在改成两条路径的地址完全不重叠：

  • wg-hub 在 sgw-ksyun 上：公网 IP，安全组开 UDP 51821，本地站点和机器人站点通过 wg-site 隧道访问 hub。
  • 独立 Peer 的 wg-hub 放在 sgw-ksyun 上（本地出口 NAT 会改写端口，经 STUN 实测无法做稳定的 UDP 入站映射）。独立 Peer 拨 sgw-ksyun 的公网 UDP 51821；控制面经 sgw-local ↔ sgw-ksyun ↔ 节点的两跳到达。NAS 访问路径见 08 存储与路径。

迁移与一致性

范围执行契约
操作与事件稳定 request ID 和请求指纹，数据库唯一约束及原子写入；同 ID 不同内容报冲突。操作记录 owner、租约和版本；恢复只处理已失效持有者，外部动作结果不明标 unknown，不自动重放。事件去重、持久游标及并发提交顺序须保证不漏读。
采集元数据collection、execution、artifact、episode 和 annotation 纳入事务及版本冲突控制。当前 JSON manifest 的 flock 和多文件替换不能作为 rclone 跨节点事务保证；大文件保留 NAS，元数据采用 staging / committed / failed，校验后提交，失败可核对恢复。
切换清点现有 SQLite 和 JSON，停写、备份、导入和核对计数、身份、引用及摘要；明确运行中操作结果未知的处置，切换后只保留一个写入源。演练备份恢复与回滚，避免丢失切换后的写入。

历史测试：本地 CIFS 上 SQLite 默认 VFS 写入失败；unix-dotfile 并发测试通过，但持锁进程强杀后残留锁。该结果只解释迁移原因，不作为共享数据库方案。

2026-11-10 代码核对：fleet/src/fleet/dashboard/state.py 目前直接使用 SQLite，默认内存数据库；create_app 启动时会将所有 running 操作标记为 unknown，明确假定单所有者。这一逻辑不能直接连接共享 PostgreSQL 后运行多个实例，否则一个实例重启会错误标记另一个实例的操作。迁移前须实现数据库级唯一约束、事务、持有者租约及仅恢复过期持有者，并验证跨进程竞争、提交顺序和故障恢复；当前未修改 Fleet 数据库或线上数据。
PostgreSQL 并发游标实测：在无网络的临时 PostgreSQL 15 容器中，事务 A 先分配事件 ID 1 并延迟提交，事务 B 提交 ID 2；消费者先看到 2，A 随后提交后以 id > 2 续读会漏掉事件 1。仅使用自增 ID 并不能保证提交顺序；迁移方案必须采用经过并发验证的提交顺序发布机制或安全游标。临时容器已删除，未连接生产数据库。
顺序发布候选方案：同一事件流的所有写入事务先以 UPDATE event_counter ... RETURNING 获取计数器行锁，在同一事务中插入事件并提交；锁直到提交或回滚才释放。隔离 PostgreSQL 15 的双进程测试中，首个事务未提交时后一个事务无法提前发布，最终以 1、2 的提交顺序可见。该方案牺牲单事件流并发写入能力；消费者持久游标、批量写入、崩溃、重试、迁移和多流隔离仍须实现并验证，当前不宣称已完成 Fleet 迁移。
现有数据库健康检查：当前 PostgreSQL 容器健康检查为 healthy，pg_isready 报 accepting connections，数据目录有持久化挂载；这不验证 Fleet 专用库、连接加密、备份或恢复能力。

Fleet PostgreSQL 迁移设计与验收矩阵记录当前 SQLite 边界、租约和事件顺序方案、停写迁移及回滚要求。

验收与恢复门槛

  • 至少两个独立进程验证并发同请求、冲突、持有者失效、进程及数据库重启、响应丢失、事件续读不漏不重，以及采集元数据事务与恢复。
  • 按约定 RPO/RTO 演练 PostgreSQL 备份恢复；数据库不可用时拒绝依赖持久化的新操作，恢复后核对未知状态，不重放机器人动作。
  • 实际 CSI 和各站点验证 NAS 权限、代码摘要、缓存可见性、断网、写回、Pod 或节点中断及恢复；不得把 dir-cache-time=5m 当作端到端可见性上限。

RLark Agent 不需要打包 CUDA 才能发现 GPU。它读取成员集群 Node 的 status.capacity 和 status.allocatable 并上报；CPU 构建的 Agent 或 Station 镜像可以承担管理与网络职责。训练镜像是否包含兼容的 CUDA 用户态库和 GPU 框架，是任务能否使用 GPU 的另一个条件。

层次职责与前提验证
宿主机与容器运行时NVIDIA 驱动、Container Toolkit 和 containerd GPU runtime 负责把设备及驱动库提供给容器；驱动不装进 RLark Agent 镜像。宿主机及 GPU 容器内分别运行 nvidia-smi。
Kubernetes 与 RLarkNVIDIA device plugin 向 kubelet 注册 nvidia.com/gpu；RLark Agent 上报该资源。节点还需启用 RLark 上报并满足调度条件。检查 Node 可分配 GPU、插件日志和 RLark Node 上报；CPU 镜像不影响资源计数。
训练工作负载镜像包含训练需要的 CUDA 用户态依赖、GPU 框架和代码；Pod 申请 GPU，并选择正确运行时。普通 CPU 版框架即使分到设备也不能执行 CUDA 训练。在实际训练镜像中验证框架 CUDA 可用性、计算及多机通信，不能只以 nvidia-smi 成功作为训练验收。

12风险与对策

四个主要风险和 Codex 逐条讨论过。每条都列出比较过的方案、采用的做法，以及采用之后还剩下什么风险。

R1 · station-api 的鉴权和租户过滤

现状：Gateway 用 HS256 对称密钥签 JWT（pkg/gateway/auth_handler.go）。GET /api/v1/users/me 返回当前用户、角色和租户（router.go）。租户只用来限制 Job、Workflow、Task、Pod（tenant_scope.go resolveTenantScope）。集群和节点是共享资源，非管理员只是看不到已下架的集群（clusters_handler.go）。

方案结论原因
共享 HS256 密钥不用拿到密钥的服务可以给任意用户签令牌，泄露面扩大
UI 经 server 的 kube 代理读 CRD不可行handleKubernetesProxy 要求客户端证书，按证书模拟身份，浏览器的 JWT 传不过去
委托 Gateway 校验采用不持有密钥，不改 Gateway
  1. station-api 和 Gateway 放在同一个入口下（例如 /station-api/），UI 用同一个 JWT 调用。
  2. station-api 收到一个 JWT 时，用它调用 /api/v1/users/me 校验。校验结果按令牌哈希缓存，最长 30 秒，且不超过令牌剩余有效期。缓存未命中且 Gateway 调不通时一律拒绝。
  3. 注意 /users/me 返回的角色来自用户 provider，而 Gateway 自己授权时用的是 JWT 里的角色（auth_middleware.go），两者可能不一致。station-api 只有在两者都是 admin 时才给管理员权限。
  4. 可见范围沿用集群规则：管理员看全部；普通用户看不到已下架集群的 Station。重绑和退役只给管理员。
  5. Station 页面不展示任务信息。以后要在 Station 上显示“正在跑哪些任务”，就要按租户过滤，到时另行设计。

剩余风险：每个请求都依赖 Gateway（缓存期内除外）；缓存期内角色变更最多晚 30 秒生效。station-api 要解析 JWT 内容但不验签，验签交给 Gateway。

R2 · 独立 Peer 离线后回程被丢弃

方案结论原因
网关上的 watchdog 按握手时间增删 /32不用没有流量时握手本来就会停，会误判；入站源地址校验也要两端同时改
每个 Peer 一个接口，跑 BGP暂不可行，但接口和路由守护进程的运维量和节点数成正比
地址不重叠 + 节点本地路由切换采用WireGuard 两端配置都不变，回退只是删一条本地路由

具体做法见 07 网络细节：独立 Peer 用 10.250.128.0/17。首期只观察；失败时不自动删除路由，自动回退是后续待验证方案。

剩余风险：切换会断开已有连接；sgw-ksyun 是独立 Peer 的单点（wg-site 单独跑，不受影响）；独立 Peer 之间的直连放到阶段 2。

证据删 Node 或重装 k8s重装系统问题

R4 · 旧 Worker 发来的指令

Codex 查了 proto/embodied-runtime/：RobotController（roscontroller/v1/robot.proto）只管理机器人进程、模式和复位，不是动作通道；camera.proto 里的 session 和 sequence 只用于相机采集。仓库里没有控制权租约。机器人的动作很可能走 ROS topic、DDS 或厂商 SDK，具体是哪条还没有确认。

方案结论原因
用 Station 的 bindingVersion 拦截无效Worker 重启时 bindingVersion 不变
在机器人上加新的指令闸门（control-gate）采用同一时间只有一个控制权持有者，带 epoch，闸门拒绝旧 epoch 的指令
只靠 RLinf 自己处理配合RLinf 要在指令里带上 epoch，否则闸门无从判断

首期为有人现场照看的机器人开发，不要求无人值守，也不宣称完成 control-gate。 每次动作前确认现场人员、急停及安全区域；失联或异常立即停止并由现场人员处置。优先做：

  1. 明确 fleet 执行器是唯一 SDK 下发口，防止同机其他进程绕过（进程隔离 / 设备独占）。
  2. VR 人工接管优先级最高，断联后机器人进入安全状态——在 fleet 仓库里做，不依赖 Station。

后续当统一轨迹层实现后再加：

  1. 新 Worker 启动时向 station-api 申请控制权，得到 (stationID, epoch)，epoch 单调递增。
  2. station-api 把新 epoch 推给机器人上的 control-gate；control-gate 写盘确认后才授权新 Worker。
  3. control-gate 只转发当前 epoch 且来自持有者的指令；租约超时时机器人进入安全状态。
前提：所有动作都必须经过 control-gate。如果 Worker 能直接发 ROS topic 或调厂商 SDK，闸门就会被绕过。这一条要先确认机器人实际用的动作通道。

Codex 确认：某工作副本中 VR 和策略经 set_cartesian_pose 下发；其他 SDK、segment 或 ROS 路径尚须逐一确认，统一轨迹层尚未实现。epoch 由 station-api 的控制权租约签发；机器人侧必须持久化当前 epoch，断联或租约超时时主动进入安全状态，而不能只信网络连接。
