# Station node identity protocol and acceptance design (prototype, not deployed)

## Scope and trust boundary

This protocol is proposed for station-api to accept node observations and authorize sensitive configuration. The current WireGuard gateway uses administrator-managed ConfigMaps and does not implement it. A cluster API credential identifies an administrator-registered member cluster; it does not authenticate a node. A Kubernetes Node UID identifies an object instance, not a credential: deleting and recreating a node must produce a conflict rather than adoption by name. A binding uses the stable member-cluster ID and Kubernetes Node UID together; display names, system UUIDs, labels and client addresses cannot substitute for them.

The member control plane, its administrators and node root are trusted; compromise of those parties is outside this protocol's isolation boundary. Preventing ordinary workloads from impersonating agents also requires restricting who can create Pods in the agent namespace, use its ServiceAccount, modify the DaemonSet and bind roles. A Pod ownerReference or label alone does not prove that a DaemonSet created it. Admission policy, RBAC and namespace isolation are deployment prerequisites and require negative tests.

## Request validation

1. Select the member Kubernetes API, TLS trust and TokenReview credential from the server-controlled cluster registration. The registered cluster ID is authoritative; never trust an API address reported by the client. Reject missing or revoked registration, connection failure and certificate failure. Never log tokens, private keys or complete Authorization headers.
2. Send TokenReview to the selected member API with the dedicated station-api audience. Check `authenticated`, the returned audience, ServiceAccount namespace/name/UID and the Pod name/UID in the authentication result. Reject missing fields rather than falling back to self-reported identity. TokenReview errors and timeouts fail closed. The issuing member cluster must match registration; a same-named ServiceAccount in another member is insufficient.
3. Read the Pod by namespace/name through a restricted read-only credential. Require the same UID as TokenReview, no deletion, the same ServiceAccount and a nonempty `spec.nodeName`. Read that Node, reject deletion, and use its actual UID as the principal. Reject client claims inconsistent with these reads. Ordinary bootstrap observations may proceed without a Station binding; sensitive operations require the configuration's member cluster, exact Station object UID, binding version and current Node UID and reject conflicts and retired Stations.
4. Issue a cryptographically random one-time challenge bound to cluster ID, Pod UID, Node UID, Station UID, binding version, operation type, request digest and short expiry. Store challenges in durable storage shared by replicas; consume them with a transactional conditional update so concurrent requests succeed at most once. Revalidate identity for a sensitive request and atomically consume a matching challenge before delivery. Reject wrong principal, altered digest, expiry and replay. If consumption succeeds but the response is lost, use a new challenge to read current desired state; do not model non-repeatable effects as edge-triggered commands. Fail closed when challenge storage is unavailable.
5. Attribute ordinary observations to the verified principal, use a server-generated receipt time and bound size, rate and fields; client time is observational only. Enforce object UID, resourceVersion and writer permissions to avoid overwriting other Stations or old instances. Configuration delivery still needs a specified secret transport, lifecycle and revocation mechanism; a ConfigMap public key is not an identity credential.

TokenReview authenticates at a point in time; it does not replace subsequent reads and authorization or prevent a trusted node with a valid token from misusing it. Short-lived tokens, one-time challenges, least privilege and member-cluster admission each address different risks. Any future cache must specify revocation latency and maximum staleness; sensitive operations fail closed on dependency failure.

On 2026-11-11, a `ChallengeStore` boundary and concurrency-safe in-process test implementation were added: the server registers a cryptographically random challenge ID; one of 16 concurrent consumers succeeds, while an unissued ID, replay, a different request digest and the expiry instant are rejected without consuming a challenge on mismatch. The memory implementation is for single-process tests only; production requires shared durable storage and a conditional transactional consume. At this checkpoint the executable station-api had not yet been added; current status is recorded below.

On 2026-11-11 the pure validator was tightened to require an authenticated TokenReview result and matching registered ServiceAccount UID, Pod name and UID, Pod ServiceAccount and node name, registered Node UID, Station UID and binding generation. Inactive bindings and empty audiences are rejected. Race tests cover these failure paths. The caller must still obtain trusted, fresh evidence from TokenReview and Kubernetes; the validator does not perform those reads.

On 2026-11-11 an injectable Kubernetes client path was added: it requests TokenReview with the registered audience, then reads the bound Pod, ServiceAccount and Node before pure validation. Multi-node clusters use a server-side `BindingResolver` keyed by the observed Node name and UID to resolve Station UID/generation rather than pinning one node in the cluster registration. Fake API race tests cover review failures, wrong audience, changed ServiceAccount/Pod UID and a recreated node. The caller must provide a trusted registration, a TLS-verified cluster client and fresh binding. Registration management, station-api, shared challenges, production RBAC and live end-to-end validation remain outstanding.

On 2026-11-11, optional `TestLiveKubernetesIdentity` ran against local cailiang Kubernetes. It created a temporary namespace, ServiceAccount and Pod-bound short-lived token, then verified the new reader accepts the token, rejects a wrong audience and rejects the token after Pod deletion. The race test passed and the namespace was removed. The test is skipped unless `STATION_TEST_KUBECONFIG` and `STATION_TEST_NODE` are explicitly set; it creates and deletes a temporary namespace. It does not validate registration management, shared challenges, authorization policy or this code path at the other sites.

Cross-site live integration was repeated on 2026-11-11 against the robot API through `10.254.240.3:6443` and the Kingsoft Cloud API at `10.254.240.2:6443`. Temporary namespaces, ServiceAccounts, Pods and Pod-bound tokens verified valid tokens, wrong audiences and invalidation after Pod deletion; both race tests passed. Temporary resources and the robot test kubeconfig were removed. This calls the library directly from the development host, not a deployed station-api, and does not cover production registration, RBAC or durable challenge storage.

On 2026-11-11, `PostgresChallengeStore` was added for a dedicated `station_api.challenges` table. Challenge IDs use 256-bit randomness; consumption uses one conditional UPDATE to atomically check subject, generation, digest, database-clock expiry and `consumed_at IS NULL`. An isolated PostgreSQL 15 race test used two independent stores and exactly one consumer succeeded; a mismatched digest did not consume the record, and expired challenges were rejected. The disposable database was removed. Schema SQL is at `apps/rlark/config/station-api-challenges.sql`; runtime must use a non-owner role with only required SELECT/INSERT/UPDATE grants; expiry pruning requires a separate janitor SELECT/DELETE role and avoids SKIP LOCKED to avoid UPDATE privileges; concurrent janitors can briefly block. PostgreSQL integration tests cover bounded pruning of only expired rows, continued consumption of live challenges and an idempotent second prune; the disposable container was removed. The store is now constructed by the executable station-api, although the sensitive routes remain unavailable until a production authorizer and action adapter are supplied. Privilege audit, pruning schedule, retention policy, backup/recovery and production deployment remain unimplemented.

On 2026-11-11 an HTTP API prototype was added in `pkg/stationidentity`: `GET /healthz`, `GET /readyz`, authenticated `POST /v1/observations`, `POST /v1/challenges`, and `POST /v1/sensitive/{operation}`. It requires a server-owned cluster registry, bounds and strictly decodes JSON bodies, attributes observations to freshly validated evidence, and consumes a one-time challenge before invoking an injected action. Failed actions do not restore a consumed challenge. A `SensitiveAuthorizer` is required and called both when issuing and consuming a challenge; missing authorizers or dependency failures fail closed, while explicit denial is returned as a generic forbidden response. Authorization is performed before challenge consumption: tests show that denial and an unavailable authorizer preserve an issued challenge for a later authorized retry. This is an authorization boundary only; no production policy adapter exists. The handler is a library prototype. A separate executable wrapper now provides HTTPS with a TLS 1.2 minimum, dependency readiness, bounded server timeouts and graceful shutdown; the Deployment does not supply sensitive authorizers or actions, so those routes fail closed. The in-memory challenge store is test-only; the executable is configured for PostgreSQL. Focused race tests cover authorization denial and unavailability as well as authentication failures, malformed/oversized input, challenge replay, action failure and readiness behavior. This does not establish production readiness.

On 2026-11-11, `KubernetesObservationSink` and `KubernetesClusterNamespaceResolver` were added. The resolver reads current RLark Cluster objects and derives scope only from the unique `spec.agentNamespace`; duplicate namespace claims and unknown clusters fail closed. The sink creates an empty `StationObservation`, then patches its status with server receipt time and the verified Node UID. It updates status only, refuses an existing object whose cluster or Station UID annotations do not match, clears fields absent from the latest snapshot, and retries create races and resource-version conflicts with a fixed bound. Focused race tests cover these behaviors. The sink is now wired to the executable but has not run against a live Station CRD. The current registry reads Cluster objects by stable object name and member credentials from the annotated `station-member-<digest>` Secret in the dedicated `station-member-credentials` namespace. Required Secret data keys are `kubeconfig`, `service-account-namespace`, `service-account-name`, `service-account-uid` and `audience`; the kubeconfig must use HTTPS, inline trust material and no exec/auth plugin or file-path credential. Secret changes refresh the cached member client. Fake API race tests cover registry ownership, rotation, binding replacement and dependency failures.

Current executable status: `cmd/station-api` is built by `make -C apps/rlark station-api` and included in the RLark image. `extensions/station/deploy/station-api.yaml`, `management-rbac.yaml` and `member-rbac.yaml` provide examples; all pass client-side dry-run but have not been applied. The Deployment is intentionally single-replica because observation rate-limit state is process-local; horizontal scaling requires a shared limiter. The workload uses external Kubernetes Secrets for its management kubeconfig, TLS keypair, database DSN and database CA bundle and keeps those credentials inside the container. Startup rejects a database DSN unless it uses `sslmode=verify-full` and references `sslrootcert`; no downgrade to plaintext or unverified TLS is allowed. The ClusterIP Service is only cluster-internal; a cross-site agent endpoint and trusted TLS certificate SAN are not selected or tested. The API database schema must be provisioned separately using `apps/rlark/config/station-api-challenges.sql`, with the runtime role separated from the migration owner. The administrator Gateway Rebind endpoint is implemented and covered by fake Kubernetes tests; it is not deployed or validated against installed Station CRDs. A production sensitive authorization/action adapter, audit query integration, credential rotation automation and live CRD status writes remain unimplemented.

The `station-agent` executable and DaemonSet example were also added. The agent reads the projected Pod-bound ServiceAccount token on every report and sends `cluster_id` plus the kernel boot time parsed from `/proc/stat`'s `btime` field over HTTPS. This timestamp is an observation only, not identity proof. A malformed or unavailable `btime` fails the report and follows the existing bounded exponential backoff; incomplete snapshots are not sent. The agent exposes loopback liveness/readiness probes, connects directly without environment-configured proxies and rejects every HTTP redirect so the bearer token remains scoped to the configured API origin. Readiness becomes true only after a successful report and expires after two intervals plus one request timeout. The server derives Pod, Node and Station identities from TokenReview and fresh API reads; the agent does not submit a self-asserted Node name. The DaemonSet uses a ConfigMap for non-secret endpoint/cluster hints and a required CA Secret, with no host configuration file or private-key mount. Local TLS integration tests cover CA verification, projected-token rotation, redirect denial, request format, boot-time parsing and readiness age; the command builds. Hardware identifiers, WireGuard peer state and active probes are not collected. Its endpoint remains an unselected placeholder, so this is not a deployed cross-site agent/API path.

## Evidence and remaining work

On 2026-11-10, local, robot and Kingsoft Cloud Kubernetes clusters were tested for Pod-UID-bound tokens, rejection of a wrong audience and rejection after Pod deletion. A further test created the same namespace, ServiceAccount and Pod names in the local and cloud clusters: each TokenReview accepted its own cluster token and rejected the other cluster’s token, with the successful audience and Pod UID checked. Submitting the same valid token again was authenticated again by both clusters, confirming that TokenReview itself does not provide one-time consumption or replay protection. The test namespaces were deleted. Current code now includes a station-api executable, dynamic registration, verified Kubernetes identity reads, Observation persistence and durable challenges; these remain undeployed prototypes. Before deployment, automated tests must cover:

- Valid identity; rejection of wrong audience, cluster, ServiceAccount, Pod UID, Node UID, binding version, retired state and deleted objects. Same-name replacement must not be adopted.
- An ordinary Pod creator cannot use the agent identity; forged ownerReferences, labels, self-reported nodes and cross-cluster tokens are rejected.
- Concurrent consumption succeeds at most once; altered digests, expiry, restart, multiple replicas, lost responses and durable-store failure have verified rejection or recovery semantics.
- TokenReview and Pod/Node read timeouts, missing permissions, network loss, TLS errors and deletion races fail closed. Audit records contain no credentials, and authorization revocation and key rotation are tested.

On 2026-11-11, a bootstrap deadlock was found and removed: the API had required an existing Station binding before accepting the Observation that the controller needs to create that Station. A fresh TokenReview and Pod/ServiceAccount/Node read now permit only the ordinary heartbeat endpoint to accept a verified but unbound Node. The initial Observation is owned by Cluster ID and Node UID. After the controller creates a Station, a subsequent report records that exact Station object UID using a resource-version-guarded metadata patch before updating status. Node replacement or a conflicting prior Station UID still fails closed. Challenge and sensitive endpoints explicitly reject unbound identity. Race tests cover unbound validation, bootstrap creation, one-time binding transition, replacement rejection and sensitive-operation denial. A handler-level fake Kubernetes integration test executes the full first-report -> Station creation -> UID-binding report -> challenge-issued sequence. This transition has not yet been exercised against a live CRD API.
