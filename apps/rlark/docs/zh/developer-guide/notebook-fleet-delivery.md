### 控制台设计方向

将拥挤的单页面拆为集群概览和选中集群的工作区。概览优先展示健康状态、容量及下一步
操作；工作区区分节点与接入、连通性、Job 和维护。接入向导先选择拓扑和版本，再逐节点
展示安装、Agent 和传输状态。混合 Job 流程先展示角色放置与资源，提交后分别呈现启动、
业务、清理进度，以及有界日志和可操作的错误信息。未知、过期和不可用不能显示为健康；
破坏性操作需要明确确认，并继续由服务端鉴权。

实现前按现有 RLark 视觉体系评审桌面与窄屏、明暗主题、键盘操作、长标识和中英文，
覆盖加载、空状态、部分失败和恢复。视觉评审不能代替 API 与运行时测试；后端契约尚未
就绪的能力不能在页面上表现为可用。

## 已确定的架构

A/B/C 是同一个 RLark 逻辑容器 Cluster 中的现有 Notebook 容器，使用 Raw 运行时，
不需要 Docker socket、systemd、TUN 或再次安装 Kubernetes。A 是网关兼计算节点，
B/C 是 Worker。RLark 通过 SSH 安装 A，A 使用自己预配置的 SSH 身份安装 Worker；
私钥不经过页面。

机器人 x86 保持在原有 Kubernetes Cluster。一个原生 Job 及扩展绑定拥有云端和
机器人 Task。RLark 将唯一 Ray head 与 B 的 rollout 调度到同一个 Raw 执行单元；
Env worker 加入同一个 Ray 集群。停止 Job 时清理这个 head 和后代，不接管或停止
现有 Job 及独立 head。

```text
RLark -- TLS 管理 :30000 --> A -- 私网 --> B/C
                             ^           B: head + rollout
                             |
                     TLS 多路复用 :30001
                             |
                      机器人 Env Pod --> S1U
```

推理数据绕过本地 RLark。SSH 只用于安装和控制，不使用 HTTP proxy、SSH 隧道、
WireGuard 或全局路由修改。A 公网使用管理 30000 和数据 30001，暂不使用 30002。
内部 Ray、Gloo 和 Fleet Driver TCP 复用数据网关。首版每个网关只接纳一个活动的
跨集群 Job。checkpoint 和模型设置属于工作负载配置，不属于集群或模型目录配置。
不实现 GPU 保活，也不实现 Notebook 电源管理。

## 实施顺序与验收

1. **基线收尾：**移除 GPU 保活的 API/UI/打包/服务行为，修复旧 UI 响应测试，
   重新生成 schema，补接入、安装器和服务管理器失败恢复测试。保留正常 GPU 发现
   和分配。Go 与 UI 检查全部通过。
2. **一键接入：**同一页面流程创建 Cluster、保存拓扑并固定版本，安装 A、建立
   管理链路，再经 A 安装 Worker。UI/CLI 共用操作 ID 和权威资源。分别显示 SSH、
   Agent、服务和数据就绪。Worker 部分失败保留已成功进度。真实验证 A/B 接入，
   C 可用时补新增节点验收。
3. **维护：**替换/退役绑定精确 UID，撤销凭据前检查 Job、allocation 和升级引用。
   清理不确定则禁止复用。重启后的 Notebook（新实例/IP）按节点名重新提交接入即可加入：
   控制器替换空闲的旧记录，旧记录仍被占用时以 `ReplacementBlocked` 等待。管理器重启保留节点服务，整套包
   通过校验。Worker 空闲升级，A 转发活动 Job 时也视为忙碌。凭据按精确身份续期，
   破坏性传输变更等待空闲。
4. **托管网络：**Job 拥有网络会话，固定参与者、Task/执行身份、地址与内部端口。
   私下分发凭据，自动为 Raw 进程树和机器人 Pod 注入 Linux/glibc TCP 连接组件。
   机器人使用共享 Pod 网络的传输 sidecar，明确配置 IPv4/Gloo 网卡。断线使既有
   流失效，重连不重放数据，也不承诺 Ray 无损恢复。先验证机器人实际网络到
   A:30001 出站，再验合成流量、Ray Actor/对象和双向 RLinf Channel。
5. **混合 Job：**预留 B、确定 head、创建 Env、配置传输、启动 head、加入 worker、
   验证成员及 Channel，最后启动 Fleet。分别上报放置、传输、head、成员、Channel、
   业务和清理条件。Env 资源仍由 Kubernetes 调度；不承诺跨运行时原子 gang 调度。
   超时清理部分启动，关键成员失败停止兄弟成员，显式重试等待旧执行清理，不无限
   自动重试整组，也不全局杀进程。
6. **页面：**新增混合/Fleet 专用提交表单，选择云端/机器人目标并提交各角色资源、
   命令、环境和配置。模型参数作为业务输入传递。展示唯一 head、成员关系、启动
   进度、有界日志和停止清理结果；API/CLI 创建的 Job 同样展示。本轮不要求额外
   暴露完整远程 Fleet Dashboard。
7. **真实验收：**重新读取当前 Notebook 实例/IP 与机器人状态，不假设历史地址
   仍在线。验证 B CPU/CUDA Job 生命周期、模型加载、同一 Ray cluster ID、Channel
   和真实 S1U Passive 推理。至少 10 分钟且完成 20 次观测/预测往返，记录加载耗时、
   延迟、失败和丢帧。停止后证明所属资源清理，保留 checkpoint，再次提交成功。

工作负载验收使用
`/ks3-regular/ss/checkpoints/test/lumo2_1022_exp1_pack_anything_pack_the_suitcase_20261023142019`。
processor、权重、归一化和接口由 Fleet 校验。Passive 不开启 Active、不下发执行
动作。保留机器人已有 Job，资源无法安全并存时等待。

## 实现与兼容边界

运行时、接入、网络和控制器集中在独立 `extensions/container-runtime` 模块，UI
组件留在 RLark 主界面。核心只增加必要且经过测试的通用适配，包括原生 Kubernetes
Agent 消费扩展 Task 前验证目标 Cluster UID。持久拓扑、一次性启动/替换操作和观测
回执分开，所有入口及直接管理 API 都校验归属、租户、UID 和 generation。

扩展现有类型化 Cluster/Node/Job 附属资源和版本合同，不开放任意远程命令。
从类型源生成 CRD/deepcopy。保留单进程 Raw 提交、Agent 单独发布和旧 Gateway
读取兼容。对应验收通过前均标为预览，基础设施阻塞与代码缺口分开记录。

### 2026-11-06 机器人中继链路

A 的管理网关现在在同一进程里同时提供 30001 端口的 Ray TCP 中继：接入配置的
`gatewayArgv` 传入 `--ray-config=/opt/rlark-ray-gateway/ray-gateway.json`，
A 只停掉 RLark 自己的服务后重新接入，A 上独立的 Fleet/Ray 和训练任务未受影响。
同时签发了有效期 30 天的新中继 CA、网关证书和 peer 证书，peer 按叶子证书做 pin。

机器人 x86 经机器人 Orin 桥接到本地路由器再出外网。x86 的 `enp2s0` 上有两个
地址：机器人局域网的 `192.168.0.10/24` 和路由器网段的 `192.168.31.250/32`。
只有 `192.168.31.0/24` 这条路由写了 `src 192.168.31.250`，默认路由没有指定
源地址，所以内核用 `192.168.0.10` 发起外网连接，路由器不会为这个地址做 NAT。
因此 x86 上访问公网 TCP 和已配置的公网 DNS 都会超时；把 socket 绑定到
`192.168.31.250` 后，同样的目标都能连通。开发机直接在路由器网段上，所以能访问 A。

中继 peer 不改系统路由，只用 `localAddress: 192.168.31.250` 绑定它到网关的
连接；按此配置，机器人 peer 已建立到 `36.103.180.181:30001` 的会话。若要在主机
层面解决，可给 x86 默认路由加上 `src 192.168.31.250`
（`ip route replace default via 192.168.0.11 dev enp2s0 src 192.168.31.250`），
并写入主机网络配置使其持久化。这一改动**尚未执行**，它会影响机器人上所有进程，
包括 DNS。

机器人部署注意事项：

- 机器人 Env 镜像 `fleet-runtime-cpu:4090-20261027-numpy2.2.6` 基于
  Ubuntu 20.04，glibc 为 2.31。连接 shim 必须针对该 glibc 编译（构建机 2.35
  编出的版本要求 `GLIBC_2.34`），中继二进制使用 `CGO_ENABLED=0` 构建。
- `/run` 以 `noexec` 挂载；中继二进制要放在可执行的主机目录，例如
  `/var/lib/rlark-ray-transport`。
- Secret 投影出来的文件是软链接，中继会拒绝这样的私钥；启动 peer 前先复制成
  私有的普通文件。
- 机器人上的 RLark Agent 镜像早于 `headAddress` 和目标 Cluster UID 校验。
  Fleet Env 容器自己读取 `RAY_ADDRESS`，因此混合 Job 在 Pod 模板里设置该变量；
  在升级该 Agent 之前，原生的目标校验不会生效。

B 和机器人的 peer 都已与 A:30001 建立会话。这条链路上还没有运行过 Ray 进程、
Fleet 服务、混合 Job，也没有执行过任何机器人动作。

### 2026-11-06 Pod 网络上的混合 Job

2026-11-06 晚（北京时间），先把机器人 Agent 升级到 `20261106-agent-67eaa39`，再以共享方式提交混合 Job `fleet-mixed-b-s1u-20261106-2`。提交顺序是：先建挂起的 Job，再建 `ContainerJob` 绑定，最后带 UID 和 resourceVersion 前置条件激活。Raw rollout 跑在 B 上，B 重启后私网地址是 `10.1.2.196`；Kubernetes Env 跑在 `s1u-01-x86` 上。这是运维人员手工组装的预览，中继还不是 RLark 自动注入的。

- **Env 改用 Pod 网络**：之前用 `hostNetwork` 时，Env 固定使用的 Ray 端口 `41001`/`41002` 和机器人主机上独立的 Ray 冲突。现在 Env 改用 Pod 网络，用 Calico 注解 `cni.projectcalico.org/ipAddrs` 固定地址 `10.242.164.100`。网关的 peer 表必须写明确的 IP，所以这个地址不能变。中继 peer 作为 sidecar 和 Env 共享同一个网络命名空间。主机上的 Ray 没有动。
- **不改路由也能出网**：Calico 的 NAT 跟随默认路由走，而默认路由没有 `src`，所以 Pod 访问 A:30001 会超时，原因和主机一样。解决办法是加一个 `hostNetwork` 的 Deployment `rlk-relay-forward`：
  - 只监听 `192.168.0.10:31030`；
  - 用 `192.168.31.250` 作为源地址，把原始 TCP 转发到 A:30001；
  - mTLS 和证书 pin 仍然是 peer 和 A 端到端的。

  机器人的默认路由仍然没有改。
- **Driver 拓扑**：Fleet Driver 只在 bootstrap 时读一次 RLinf 拓扑。所以 B 的启动脚本要等所有 Ray 成员都 Alive，才启动 Driver。另外 RLinf 要求 `RLINF_NODE_RANK` 要么每个节点都设置、要么都不设置，Env 设了 rank `1`，所以 head 设 rank `0`。没有这两处改动时，Driver 只看到 1 个节点，bootstrap 失败。
- **GPU 共用**：Notebook 上的 `gpu_keepalive` 一直保持运行，rollout 配置里设了 `allow_shared_accelerators: true`。Fleet 启动后，keepalive 会从约 40 GiB 降到很小的占用。
- **节点选择**：接入流程和原生 Node 都不会设置 `rlark.io/node-name` 标签。所以要把 Raw Task 固定到某个 Notebook 上，需要手工给原生 Node 加这个标签，并带 UID 和 resourceVersion 前置条件。

观测到的结果：Driver 报告 `num_nodes: 2`，rank 0 是 `10.1.2.196`，rank 1 是 `10.242.164.100`；rollout 已经在 keepalive 旁边加载完权重。机器人只有在运维人员从 Fleet UI 发起 rollout 时才会动。这还不是第 7 项要求的 10 分钟 Passive 验收。
