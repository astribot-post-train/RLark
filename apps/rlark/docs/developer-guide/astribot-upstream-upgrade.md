# Astribot review of upstream RLark

The reviewed range is `9ad4a21..d06745e`. The feature changes came from `8c3a72d`, and `d06745e` corrected the release workflow and added the v0.1.0 changelog. The Astribot branch contains `d06745e` and all 211 paths added in the upstream range. Keep the integration evidence below separate from acceptance on a deployed environment.

The standard Astribot release applies CRDs and the generated management roles in its `crds-rbac` stage. The Astribot image inventory builds `rlark-upgrade` from the upstream recipe. Verify that the actual candidate image is published and pullable by digest before accepting batch upgrades. The upstream v0.1.0 image list does not include it. The stock upgrade Job regenerates a cluster Deployment and node DaemonSet from `DeployConfig`. Keep Astribot installations with custom mounts, arguments or embedded topology on their own rollout path until an upgrade and rollback preserve the required configuration. The upstream Kubernetes workload path remains at preview maturity. Docker and Raw workload execution are unimplemented.

## Implementation in the compatibility branch

Astribot implements station controls, observation, camera and log proxy, discovery, and the model catalog in `apps/rlark/astribot/stations/`. The admission workflow, join-code validation, bootstrap command and admission projection live in `stationidentity/`. The member network planner and machine setup scripts live in `provisioning/`. The Addon catalog, Agent readiness, node-service proxy, task adapters, storage declaration rendering and OCI manifest checks have their own Astribot packages. Console extensions and tests live under `apps/rlark-ui/src/astribot/` and `apps/rlark-ui/tests/astribot/`.

Keep canonical CRD fields and generated artifacts, shared roles, authorization and error conversion, component wiring, and tests that exercise the shared entry points next to their upstream contracts. The stock `csi-driver-rclone` entry carries Astribot parameters used by existing installations of the same Addon name and version. Remaining shared-package implementation includes the SSH join workflow, cluster provisioning orchestration, registry access, and storage persistence and reconciliation, and Agent and provider code that uses private controller state.

The reconciliation branch includes the v1.7.3 S1U telemetry source from the release build. The same hardware capability profile is embedded by Gateway and copied into the S1U image. Validate body state, both camera streams, the camera timing metrics, and site discovery in a test environment before using this branch for a release.

The release tool acquires member Kubernetes Leases in sorted order before release writes, while retaining the management-plane site Lease. On a conflict it reports the holder and releases any member Leases already acquired. Before using this release tool, an administrator must apply the member release RBAC and provision `astribot/release/member-upgrade-lease.yaml` in each target cluster. Expiry alone does not clear a member holder. A takeover requires independent evidence that the old writer exited. Do not use an older release tool concurrently because it only knows the site Lease.

The upgrade reconciler reads results through the driver interface. It accepts structured failure diagnostics from the owned upgrade container and ignores arbitrary termination text. The image-only executor and ConfigMap checkpoint have local tests for preserving the template, first-upgrade rollback, and resuming rollback. The isolated-test `astribot-cluster-only` mode now connects the Agent, a separate Job and the executor. The Agent uses a trusted local policy to pin the executor digest, name the Job by the child UID and mount immutable configuration. The Job uses a dedicated ServiceAccount, checks its Pod and Job UIDs, and edits only the local Agent Deployment's image fields under the member lease. It refuses a member where a node Agent DaemonSet exists. A child created directly through the management API still passes the member policy checks. The Gateway continues to guard declared Astribot targets against the stock installer. Managed node Agents still require the restricted management endpoint and full upgrade-and-rollback validation on isolated clusters.

For a frontend-only hot build, run `astribot/release/build-ui-static.sh` with a new absolute output directory. It matches the production image’s IAM build setting and includes the standalone `login.html` and its images. Verify both the unauthenticated redirect and the authenticated console before closing a hot deployment.

For an isolated member, verify that its management `Cluster.spec.nodeAgents` is disabled before using this mode. Apply the member upgrade Lease and `astribot/release/member-upgrade-cluster-only.yaml`, using the member's real Deployment name in the Role. A member administrator creates the `rlark-agent-upgrade-policy` ConfigMap in `rlark-system` with `mode=astribot-cluster-only`, `deployment`, and a digest-pinned `executorImage`. Create a test `ClusterUpgradeJob` for that member using the same executor digest and a DeployConfig containing only the two digest-pinned image fields `kubernetes.agent-image` and `kubernetes.image`. This entry point is for isolated validation.

An isolated Kind run exercised the executor with a real Kubernetes Job and an Agent-shaped workload fixture. A healthy update rolled out. An intentionally broken image entered CrashLoopBackOff and the independent Job restored the previous image, preserved unrelated arguments and released the member lease. This verifies the executor path. The Agent launcher and its immutable config are covered separately by Go tests.

The Gateway, management controller, and updated member Agent require `rlark.io/upgrade-driver: stock` for the stock installer. A managed node Agent declaration rules out stock execution even with explicit opt-in. The Agent also requires that the member have no Astribot lease without an executor policy. For the isolated-test image-only mode, the Job writes a completion checkpoint under the member lease after the target is ready. If the local Job disappears, the Agent checks that the checkpoint belongs to this child UID and that the same Deployment is ready with both requested image digests. An absent or mismatched checkpoint is reported as an unverified outcome.
