# Astribot review of upstream RLark

The reviewed range is `9ad4a21..d06745e`. The feature changes came from `8c3a72d`, and `d06745e` corrected the release workflow and added the v0.1.0 changelog. The Astribot branch contains `d06745e` and all 211 paths added in the upstream range. Keep the integration evidence below separate from acceptance on a deployed environment.

| Area | Branch integration | Environment acceptance |
| --- | --- | --- |
| Data-plane batch upgrades | The shared upgrade page, Gateway API, both CRD schemas, Controller Manager reconciler and Agent executor are present. Astribot management identities now grant the Gateway access to upgrade jobs and the Controller Manager access to reconcile and report them. The data-plane Agent's cluster-scoped management role already includes the child resource and its status. | Apply the CRDs and RBAC before enabling use. Use an approved `rlark-upgrade` image and test a disposable Kubernetes cluster, including concurrency, timeout, failure threshold and rollback. Verify Agent arguments, volume mounts, credentials and topology before expanding to Astribot-managed clusters. |
| Node lifecycle | Node management retains heartbeat and schedulability, cordon, drain progress, undrain, recovery and removal. Both confirmation dialogs now describe explicit Job start after a drain. Astribot station removal remains a separate flow. | On an idle test node, verify drain completion, then resume scheduling and confirm affected tasks stay stopped until their Job is explicitly started. Verify the station removal flow separately. |
| Scheduling and diagnosis | Job creation retains cluster and node selection, capacity and schedulability filtering, and `/dev/shm` configuration. Worker diagnostics retain scheduling, storage and image-pull reasons. The Kubernetes owner-chain validation and status projection also cover Astribot DaemonSets and per-node task instances. | Run Kubernetes jobs that exercise node selection, a waiting worker and the shared-memory mount. Compare the Pod and Task status with the worker UI. Verify a DaemonSet owner UID mismatch and replacement Pod do not leak old status, and that per-node instances update and clear. |
| Agent, recovery and deployment | Startup configuration validation, dependency and permission checks, periodic repair, ownership checks, Helm charts and the release workflow are present. The control-plane chart copies match the canonical CRD schemas. | Exercise Agent restart and self-repair, disk-pressure recovery and ordinary controller startup in a test cluster. Render and install both charts in an isolated environment to check the upstream deployment path. Astribot retains its own deployment process. |

The standard Astribot release applies CRDs and the generated management roles in its `crds-rbac` stage. The Astribot image inventory builds `rlark-upgrade` from the upstream recipe. Verify that the actual candidate image is published and pullable by digest before accepting batch upgrades. The upstream v0.1.0 image list does not include it. The stock upgrade Job regenerates a cluster Deployment and node DaemonSet from `DeployConfig`. Keep Astribot installations with custom mounts, arguments or embedded topology on their own rollout path until an upgrade and rollback preserve the required configuration. The upstream Kubernetes workload path remains at preview maturity. Docker and Raw workload execution are unimplemented.

## Implementation in the compatibility branch

The station running-images implementation, robot model catalog and console brand assets/configuration now live in the per-project Astribot directories. Gateway route registration, error translation and its integration test stay beside the shared route code. The remaining station Gateway groups, task adapters and UI overrides still need migration.

The release tool acquires member Kubernetes Leases in sorted order before release writes, while retaining the management-plane site Lease. On a conflict it reports the holder and releases any member Leases already acquired. Before using this release tool, an administrator must apply the member release RBAC and provision `astribot/release/member-upgrade-lease.yaml` in each target cluster. Expiry alone does not clear a member holder. A takeover requires independent evidence that the old writer exited. Do not use an older release tool concurrently because it only knows the site Lease.

The upgrade reconciler reads results through the driver interface. It accepts structured failure diagnostics from the owned upgrade container and ignores arbitrary termination text. The image-only executor and ConfigMap checkpoint have local tests for preserving the template, first-upgrade rollback, and resuming rollback. They still require the Agent-to-Job wiring, dedicated Job permissions, and a restricted management endpoint for the declared node Agent image. The Gateway now preflights named and selector-based targets. It validates configuration for declared Astribot targets and stops them before the stock installer can run. Agent-side checks for child jobs submitted directly to the management API and isolated-cluster validation remain pending. Keep the Astribot batch action out of operational use until those paths are complete and verified.

For a frontend-only hot build, run `astribot/release/build-ui-static.sh` with a new absolute output directory. It matches the production image’s IAM build setting and includes the standalone `login.html` and its images. Verify both the unauthenticated redirect and the authenticated console before closing a hot deployment.
