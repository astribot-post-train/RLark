# Astribot review of upstream RLark

The reviewed range is `9ad4a21..d06745e`. The feature changes came from `8c3a72d`, and `d06745e` corrected the release workflow and added the v0.1.0 changelog. The Astribot branch contains `d06745e` and all 211 paths added in the upstream range. Keep the integration evidence below separate from acceptance on a deployed environment.

The standard Astribot release applies CRDs and the generated management roles in its `crds-rbac` stage. The Astribot image inventory builds `rlark-upgrade` from the upstream recipe. Verify that the actual candidate image is published and pullable by digest before accepting batch upgrades. The upstream v0.1.0 image list does not include it. The stock upgrade Job regenerates a cluster Deployment and node DaemonSet from `DeployConfig`. Keep Astribot installations with custom mounts, arguments or embedded topology on their own rollout path until an upgrade and rollback preserve the required configuration. The upstream Kubernetes workload path remains at preview maturity. Docker and Raw workload execution are unimplemented.

## Implementation in the compatibility branch

Astribot implements station controls, observation, camera and log proxy, discovery, and the model catalog in `apps/rlark/astribot/stations/`. The admission workflow, join-code validation, bootstrap command and admission projection live in `stationidentity/`. The member network planner and machine setup scripts live in `provisioning/`. The Addon catalog, Agent readiness, node-service proxy, task adapters, storage declaration rendering and OCI manifest checks have their own Astribot packages. Console extensions and tests live under `apps/rlark-ui/src/astribot/` and `apps/rlark-ui/tests/astribot/`.

Keep canonical CRD fields and generated artifacts, shared roles, authorization and error conversion, component wiring, and tests that exercise the shared entry points next to their upstream contracts. The stock `csi-driver-rclone` entry carries Astribot parameters used by existing installations of the same Addon name and version. Registry access and Agent/provider integration that depend on shared component state retain their current integration points.

The reconciliation branch retains the S1U telemetry source and the target branch’s v1.7.4 Addon catalog. Verify telemetry against the candidate image digest, since the historical v1.7.3 catalog label alone does not establish its presence. The same hardware capability profile is embedded by Gateway and copied into the S1U image. Validate body state, both camera streams, the camera timing metrics, and site discovery in a test environment before using this branch for a release.

The release tool holds the management-plane site Lease and acquires member Kubernetes Leases in sorted order before release writes. For an existing member with the standard release RBAC, it adds the Lease rules to the existing release Role and creates the Lease when missing. Conflicts report the holder and release any locks acquired by this attempt. An expired release CLI holder can be replaced, and every member write rechecks its Lease. A different operation can take over an expired holder when the old executor is terminal, or when the old Pod and its UID-bound Job are proven gone. If the old Job remains active, its replacement Pod retains priority. An older lease record without the Job UID still requires positive termination evidence. The release tool preserves its member Lease and Job-read RBAC when applying older release trees. Use one generation of release tooling at a time.

The image-only executor retries temporary member API failures within the phase budget and checks live Pod, Job and Lease identity before each write. A confirmed loss of ownership interrupts the executor so an eligible replacement Pod can resume the checkpoint. The upgrade reconciler reads results through the driver interface. It accepts structured failure diagnostics from the owned upgrade container and ignores arbitrary termination text. The image-only executor and ConfigMap checkpoint have local tests for preserving the template, first-upgrade rollback, and resuming rollback. The isolated-test `astribot-cluster-only` mode now connects the Agent, a separate Job and the executor. The Agent uses a trusted local policy to pin the executor digest, name the Job by the child UID and mount immutable configuration. The Job uses a dedicated ServiceAccount, checks its Pod and Job UIDs, and edits only the local Agent Deployment's image fields under the member lease. It refuses a member where a node Agent DaemonSet exists. A child created directly through the management API still passes the member policy checks. The Gateway continues to guard declared Astribot targets against the stock installer. Managed node Agents still require the restricted management endpoint and full upgrade-and-rollback validation on isolated clusters.

Image-only Jobs use bounded Pod replacement for executor loss. A replacement in the same Kubernetes Job and child can resume the persisted checkpoint after the previous Lease expires, even if the old Pod is gone. Every executor write revalidates its live Pod, owning Job and Lease. A different Job cannot infer termination from a missing Pod. The Agent waits for terminal Job conditions, so one failed Pod does not fail a still-running child. The Job deadline and managed grant include recovery time. Deletion of the whole Job still requires a verifiable completed checkpoint to report success.

In an isolated Kind run, the executor Pod was force-deleted after writing the checkpoint and changing the Agent Deployment. The test advanced the old Lease timestamp to simulate expiry. Kubernetes created a different Pod under the same Job UID, which reused the checkpoint, completed the rollout and released the Lease.

Managed rollouts use DaemonSet status when fully converged. During a degraded rollout, the broker verifies Pods owned by the original DaemonSet and the corresponding member Nodes. At least one Ready Node must run the expected, Ready Agent, every other Ready target must do so as well, and only explicitly NotReady or Unknown Nodes with attributable Pods can be deferred. A missing Pod or a returning Node on the old image prevents readiness. Rollback restores the node Agent image declaration before waiting for the cluster Agent Deployment, so a stalled Deployment does not suppress node image restoration. The broker's member verifier needs namespaced Pod list and cluster Node list permissions.

For a frontend-only hot build, run `astribot/release/build-ui-static.sh` with a new absolute output directory. It matches the production image’s IAM build setting and includes the standalone `login.html` and its images. Verify both the unauthenticated redirect and the authenticated console before closing a hot deployment.

For an isolated member, verify that its management `Cluster.spec.nodeAgents` is disabled before using this mode. Apply the member upgrade Lease and `astribot/release/member-upgrade-cluster-only.yaml`, using the member's real Deployment name in the Role. A member administrator creates the `rlark-agent-upgrade-policy` ConfigMap in `rlark-system` with `mode=astribot-cluster-only`, `deployment`, and a digest-pinned `executorImage`. Create a test `ClusterUpgradeJob` for that member using the same executor digest and a DeployConfig containing only the two digest-pinned image fields `kubernetes.agent-image` and `kubernetes.image`. This entry point is for isolated validation.

An isolated Kind run exercised the executor with a real Kubernetes Job and an Agent-shaped workload fixture. A healthy update rolled out. An intentionally broken image entered CrashLoopBackOff and the independent Job restored the previous image, preserved unrelated arguments and released the member lease. This verifies the executor path. The Agent launcher and its immutable config are covered separately by Go tests.

The Gateway, management controller, and updated member Agent require `rlark.io/upgrade-driver: stock` for the stock installer. A managed node Agent declaration rules out stock execution even with explicit opt-in. The Agent also requires that the member have no Astribot lease without an executor policy. For the isolated-test image-only mode, the Job writes a completion checkpoint under the member lease after the target is ready. If the local Job disappears, the Agent checks that the checkpoint belongs to this child UID and that the same Deployment is ready with both requested image digests. An absent or mismatched checkpoint is reported as an unverified outcome. With a stock-only batch, successful rollback is recorded separately and does not consume failure tolerance, matching upstream `d06745e`. In a mixed batch, a successful managed rollback still consumes Astribot’s failure budget. A successful stock rollback does not. Stock keeps the upstream Job retry and deadline semantics. Explicit driver opt-in, the fail-closed batch preflight, and the requirement for an approved digest-pinned stock executor on a release-managed member are Astribot compatibility boundaries.

The machine list and admission eligibility use the shared projection in `stations/machine_view.go`. Cluster provisioning and SSH node admission share installer streaming, digest verification, and progress reporting in `provisioning/bundle.go`. Astribot S3 mount option and endpoint validation lives in `storageconfig/mount_request.go`, using the upstream endpoint normalizer. The Gateway applies the existing authorization and response contracts before dispatching to the Astribot workflows. Astribot also owns the projection of target rejection details and node join annotations to the existing API fields.

The executor treats a managed node Agent image as a third, independent target and persists it in the attempt checkpoint. Enabling managed upgrades still requires a management-plane path restricted to comparing and changing `Cluster.spec.nodeAgents.image` for the verified cluster and attempt, plus local rollout verification. Keep the batch gate closed for Astribot members until that path passes a mixed-cluster test.

### Managed node Agent upgrade boundary

The release command now compares the enabled node Agent image declaration against the live stage snapshot. It checks the Cluster UID, keeps the resource version for the write, and rechecks the member lease before changing the image. A different image, a replaced or deleting Cluster, or a disabled declaration stops the image change. A retry that sees the target image succeeds after verifying ownership and the lease. The selector, rollout policy and other Cluster fields stay intact. Provisioning an enabled declaration stays in the release bootstrap path.

The cluster-only Job uses its attempt checkpoint for image-only execution. The Agent observes a local Job only when the Job name, child UID label and executor ServiceAccount match. The upstream installer keeps using `rlark-state` for its rollback baseline. The image-only Agent never writes that shared record after a Job releases its lease.

For the managed mode, the control-plane authorization and the member rollout must survive a restarting or unhealthy cluster Agent. Keep UpgradeJob and ClusterUpgradeJob as the operator-facing resources. Use a control-plane-owned grant bound to the Cluster UID, child UID and approved target digest, with its rollback baseline recorded by the control plane before the first write. A member Job must present attempt-bound credentials. The control plane must independently verify the member Job and current member lease, expose only the scoped image operation, and keep approval and credentials out of member-writable status. Do not mount a general Cluster writer or the site's release credential in the member Job. The cluster Agent remains the sole reconciler for its node Agent DaemonSet. Success requires evidence for the same workload instance, target image and current rollout, including replacement Pods, after the declaration write. The node Agent image is independent of the cluster Agent and tools images.

The standalone broker and Job adapter are available for isolated managed-mode validation. The operator installs the existing executor ServiceAccount, checkpoint and lease, then applies `astribot/release/member-upgrade-verifier.yaml` to each disposable member. The verifier can submit TokenReviews and read the member's executor Pod, Job, Lease and node Agent DaemonSet. Its credential is mounted in the broker only. Run `rlark-upgrade` with `RLARK_NODE_IMAGE_BROKER_CONFIG` pointing to a JSON configuration with `listen`, `tlsCert`, `tlsKey`, `managementKubeconfig` and `members`. Each entry in `members` is keyed by the management Cluster name and contains `clusterUID` and `kubeconfig` for its member verifier. Use a dedicated management identity allowed to get and update only the approved Cluster names. The broker listens on a specific internal address and requires direct TLS.

For an isolated child, set the local `rlark-agent-upgrade-policy` ConfigMap to `mode=astribot-managed-node`, with `deployment`, digest-pinned `executorImage`, HTTPS `brokerOrigin` and trusted PEM `brokerCA`. Managed DeployConfig requires `kubernetes.agent-image`, `kubernetes.image` and `kubernetes.node-agent-image`, all pinned by digest. A trusted management operator stages `rlark.io/node-image-upgrade-grant` on the Cluster before starting that child. This JSON grant contains `ClusterUID`, `DaemonSetUID`, `ChildUID`, `Before` (the observed, digest-pinned node Agent image), `Target` (node Agent target), `Deployment` (the approved `Agent` and `Tools` digests), `ExecutorImage`, `Expires` (RFC 3339, beyond the Job deadline to allow rollback) and `Phase` initially set to `Approved`. Never replace an active grant. The Job uses a rotating Pod-bound token for the broker's dedicated audience. The broker changes only the image and the grant phase with one Cluster resource-version check, so a late forward request cannot undo a rollback. It verifies the same managed DaemonSet UID, expected template image, observed generation and updated and available counts. The broker checks convergence on eligible nodes. A node excluded as unavailable at rollout start is not counted as an upgrade or rollback blocker.

If the managed Job has been cleared, recovery verifies the same child’s completed checkpoint, the live Agent Deployment and managed DaemonSet, and the applied Cluster grant. An expired grant is still read-only evidence for the same attempt. Changed or missing evidence results in an unverified outcome. Before enabling batches, verify stock and managed members together, including expired grants, resource replacement, lease conflicts, partial rollout and rollback. Confirm that a member cannot change another Cluster or fields outside the approved image.

A separate Kind fixture exercised the managed binary as a real Kubernetes Job with a projected bound token, the standalone HTTPS broker and scoped verifier credentials. A fixture reconciler propagated the approved declaration into a real DaemonSet and the Job waited for rollout status. A withheld rollout timed out, restored the original declaration without changing its selector and released the member Lease. This test does not exercise the full Astribot node Agent reconciler, production kcp integration or mixed batch scheduling.

### Mixed-batch activation

Configured mixed batches use the shared `UpgradeJob`, with an Astribot `BatchDeployConfig` YAML document in `spec.configPatch`. Its `apiVersion` is `astribot.rlark.io/v1alpha1` and `kind` is `BatchDeployConfig`. Set `stockDeployConfig` to the full stock Kubernetes DeployConfig, or to an explicitly empty string to reuse the stock member's saved configuration. Stock members use `spec.image`. The `managed` mapping has `executorImage` and `deployConfig`, the latter as a YAML string containing the three approved images. The controller creates one upstream child resource per cluster with only that driver's config and image. A managed attempt that rolls back counts against failure tolerance. A rolled-back standard attempt retains the upstream counting behavior. Legacy stock requests continue to accept an ordinary DeployConfig.

Managed batch dispatch requires the trusted Cluster declaration `rlark.io/upgrade-driver: astribot-image-only` and `rlark.io/managed-upgrade-batch: enabled`. Before setting these, upgrade and reconnect the member Agent with the managed policy and confirm broker reachability. Set `autoIssueBatchGrants: true` in the broker config and pin `executorImage` in each broker member entry. The broker's management identity additionally needs `get` on UpgradeJobs and selected member ClusterUpgradeJobs, and `create` on SubjectAccessReviews. On the first authenticated request under the member Lease, the broker checks effective member permissions, verifies the exact owned child against its parent and the selected Cluster UID, then records a grant from the live converged node Agent baseline. It refuses to reissue a grant for the same child. Member Agents only read child specs and write status. A stale Agent role allowing spec mutations blocks automatic approval.

No production Cluster is opted in by these changes. Validate the target workspace and member Agent versions before enabling the managed annotation in production.

The Kind mixed-batch fixture ran the real control-plane reconciler against the stock and managed Cluster records, confirmed distinct child specs, and used real TokenReview and SubjectAccessReview for automatic grant issuance. The managed Job completed a fixture DaemonSet rollout and restored its declaration after a second rollout timed out. The stock child was checked at dispatch, without running a stock installer. The full Astribot reconciler and production kcp workspace remain separate acceptance checks. Gateway's machine admission now delegates request validation, profile checks and persistence to the Astribot stations package. A disposable kcp v0.30.0 workspace separately confirmed that SubjectAccessReview reports the Agent's old child-spec write permission and denies it after the Role is tightened.

### Full mixed-batch fixture

A separate run used a kcp v0.30.0 root workspace and two Kind members. It ran the existing batch reconciler, both member upgrade reconcilers, the stock installer, and the Astribot node Agent and rollout reconcilers against the real APIs. Both children and the batch reached Succeeded. The stock Job updated the cluster Agent Deployment and standalone node Agent DaemonSet. The managed Job updated the node Agent through its Cluster declaration and kept the existing cluster Agent arguments. The application containers were health fixtures, while Kubernetes rollout, broker authentication and controller behavior were real. This does not use production credentials or test Agent-to-Server tunneling. A failing node Agent image timed out and the same DaemonSet UID returned to its previous image through the real reconcilers. With the member release Lease held by a simulated release, the managed child reported the holder and the zero failure tolerance stopped the queued stock child. The declaration remained unchanged.

The stock Job selects the native upstream component profile explicitly. It keeps both standard data-plane workloads in its precheck, upgrade and rollback. Ordinary Astribot installation uses its managed declaration profile. Stock batch validation and the installer share the same strict DeployConfig parser, including the documented kebab-case YAML keys.

### Gateway ownership and integration points

- `astribot/provisioning/workflow/` owns SSH node join and cluster provisioning, including request validation, stage state and recovery, host and tunnel setup, and cleanup. It uses the verified Station bootstrap client and typed management API clients. Retry returns HTTP 409 if the saved stage is unrecognized. The join list retains records that lack a completion timestamp.
- `astribot/storageconfig/` owns declaration validation and rendering, the storage Secret repository, endpoint reconciliation, and extending shared S3 storage to a new cluster. Gateway retains the existing storage routes, HTTP error mapping, and the object-browser client cache. Provisioning retries reconcile missing endpoint declarations after a partial write. The provider catalog and S3 client stay in the upstream `pkg/gateway/storage` package and are reused by the extension.
- Gateway attaches the shared JWT and admin middleware, supplies the authenticated actor and Station namespace resolution, and wires the existing certificate, Kubernetes proxy, registry credentials, Addon publishing, job-secret delivery, and log access. These hooks use the shared Gateway's authenticated clients. Canonical CRDs and generated clients stay with the API.

Cluster provisioning reserves the management Cluster and records its UID before Agent registration. A live Cluster whose UID is unbound or different returns HTTP 409 before cleanup. Existing Secret and SiteNetwork ownership checks still apply. Host cleanup verifies the original SSH host and operation marker, then verifies either the recorded native cluster UID or the original installer journal for an incomplete install. If the attempt stopped before claiming a clean host, host cleanup is a no-op. An initialized control plane still needs to answer so the installer can check for other nodes and take a snapshot. If the original host cannot be recovered, verify it separately before choosing `machine_gone`.

The SSH installer records the original native Node UID as soon as the Kubernetes boot ID matches the host, even before Ready. Cleanup uses an identity-bound Remove operation when that UID is available. With no UID, the operator can provide SSH credentials to clean a verified unused admission and tunnel, or select `machine_gone` to clear the failed attempt. An already redeemed or unverified admission and its tunnel are preserved for follow-up in Site Nodes. Cleanup never derives a removal target from the current same-named Node. For newly installed SSH nodes, a completed UID-bound host reset also clears the matching tunnel ownership marker so the host can rejoin. Legacy hosts with artifacts and no matching receipt require explicit verification. Publish the updated installer bundle and Station Controller alongside the Gateway to enable these paths.

Tunnel-based SSH joins record the member and node name alongside the attempt marker. An owned residual worker can be reset before retry or cleanup if the member API confirms a native Node NotFound. A live node of the same name, an unavailable member API, an active installer, a control plane, or missing ownership evidence blocks that reset. The Gateway also checks a recovered Node UID receipt against the native member API before persisting it. Historical SSH tunnel cleanup and reuse require a pinned SSH host, the matching WireGuard public key, no active installer or control-plane installation, and a native Node NotFound response from the member API. The host rechecks both its prior marker fingerprint and the tunnel document under the same lock before changing ownership. This also handles an absent historical marker. A same-named replacement, a different key or an unreachable member blocks cleanup. For workers without a join identity marker, verify the installer’s original node name and the API server and CA fingerprint against the member API. The administrator migration endpoint records independently reviewed Cluster, credential, SiteNetwork and native control-plane identities. See `astribot/docs/legacy-provision-migration.md` for requests and recovery. A compatible release initializes standard members only after their cluster Agent rollout and only after explicit stock opt-in. The plan and write paths share the reconciliation rules for release-owned executor RBAC. Active upgrade Jobs defer the affected member for this stage and leave its existing executor configuration in place. The release reports the member and Job and retries it on the next run.

### Server tunnel smoke test

A separate isolated run used a kcp v0.30.0 root workspace, one Kind member, and locally built Server, Cluster Agent and Node Agent binaries. The Agents connected with Server-issued client certificates and renewed their management heartbeat Leases. Authenticated requests to `/api/proxy/:agent/api/kubernetes/api/v1/nodes` and `/api/nodeproxy/:agent/:node/api/kubernetes/api/v1/nodes/:node` read the actual member API. The node-specific route returned HTTP 502 for an unconnected node without falling back to the cluster tunnel. The Server rejected a request without a client certificate. After the test Server restarted, both Agents reconnected and the same reads succeeded again. This run covers the Agent reverse tunnels. Machine admission over SSH, the Station WireGuard path, and the production upgrade rollout are separate acceptance paths.
